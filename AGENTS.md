## Обзор проекта

Мы создаем "Mini-CRM" для одного пользователя. Система анализирует архив электронной почты (~19 000 писем), извлекает с помощью LLM контакты, организации и коммерческие предложения, обрабатывает их и сохраняет в базу данных SQLite. Результаты доступны пользователю через веб-интерфейс на React.

## Обязательные артефакты и отчётность

### Структура документации для задач
При получении новой задачи создавай отдельную папку внутри `.kiro/specs/` с названием, отражающим суть задачи и дату (например: `api-pipeline-analysis-2025-10-17`).

Внутри папки задачи создавай следующие файлы:
- **`README.md`** — обзор задачи, цели, статус, ссылки на другие документы
- **`TASKS.md`** — чек-лист задач для данной конкретной задачи:
  - Формат: `[ ]` (todo), `[-]` (in-progress), `[x]` (done)
  - Приоритеты: 🔴 P0 (критично), 🟠 P1 (важно), 🟡 P2 (полезно)
  - Ссылки на коммиты/PR/артефакты
  - Краткие заметки по рискам
- **Аналитические отчёты** (по необходимости):
  - `*_ANALYSIS.md` — анализ проблем, root cause analysis
  - `IMPLEMENTATION_REPORT.md` — отчёт о реализации
  - `COMPLETION_REPORT.md` — финальный отчёт о завершении
  - Другие специфичные для задачи документы

### Правила работы с документацией:

1. **Одна задача = одна папка** — не смешивай разные задачи в одной папке
2. **Атомарность** — каждая папка должна быть самодостаточной
3. **Хронология** — включай дату в название папки для отслеживания истории
4. **Полнота** — все артефакты задачи должны быть внутри её папки
5. **Ссылки** — используй относительные ссылки между документами внутри папки

## Основные цели
1) Сквозной конвейер: Fetcher → OCR → LLM → Validation/Normalize/Dedup/Enrich → SQLite (`crm.db`).  
2) Экспорт в Google Sheets/локальные таблицы.  
3) Минимальный FastAPI + React PWA (поиск, карточки, реестр КП, модерация, просмотр письма).  
4) Напоминания по срокам КП (UI).  
5) Backlog: добавить в fetcher опцию сохранения `.eml` (низкий приоритет).

## Ожидаемый результат
- Файл `crm.db` с таблицами: organizations, contacts, contact_phones, commercial_offers, interactions, moderation_inbox.  
- Папка `data/llm_results/DATE/*.json` — сырые ответы LLM. 
- Минимальный UI (поиск, карточки, реестр КП, модерация, просмотр письма).

## Технические детали
- Язык бэкенда: **Python 3.11 (FastAPI)**.  
- БД: **SQLite** (миграция на Postgres позже без смены моделей домена).  
- Фронтенд: **React + Vite + Tailwind**, PWA.  
- Валидация JSON: **Pydantic/jsonschema**.  
- OCR: локальные экстракторы + Google Vision fallback.

## Стиль кодирования
naming: "snake_case для функций, PascalCase для классов"
organization: "Один класс = один файл, промпты отдельно"

principles:
    - "Всегда добавляй типизацию (typing) к функциям"
    - "Используй docstrings с эмодзи для описания функций"
    - "Включай обработку ошибок с информативными сообщениями"
    - "Логируй операции с эмодзи (🔍, ✅, ❌, 🔧, 📊)"
    - "Создавай fallback системы для критических операций"

- Логи в `data/logs/` с уровнями INFO/WARN/ERROR.  
- Отчёт по качеству: доля валидных JSON, число сущностей, размер Inbox.  
- Idempotency: повторный запуск не должен плодить дубли.

## Процедура запуска (тонкий слой → основной пайплайн)
1) Запусти `api_pipeline_validator.py` (см. 12_API_PIPELINE_VALIDATOR.md).  
2) Проведи 1–2 итерации качества, оформи отчёты в `contact_parser/memory-bank/reports/`.  
3) После стабилизации — **перейди на `main_new.py`** и используй его режимы (`interactive/test/full-pipeline/async-*`) для полноценной обработки.  
4) Убедись, что ядро конвейера не дублируется, а импортируется общими модулями.
