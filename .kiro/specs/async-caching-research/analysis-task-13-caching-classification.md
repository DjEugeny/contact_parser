1. Процессы, которые МОЖНО кэшировать
1.1 OCR результаты ✅ ВЫСОКИЙ ПРИОРИТЕТ
Описание: Извлечение текста из PDF/изображений

Критерии кэшируемости:

✅ Детерминированный результат (один файл → один текст)
✅ Дорогая операция (1-5 секунд на документ)
✅ Стабильный результат (файл не меняется)
✅ Высокая частота повторных запросов
Ключ кэша:

# Текущая реализация
key = MD5(filename + file_size + mtime)

# Рекомендуемая реализация
key = MD5(file_content_hash)  # SHA256 содержимого файла
Механизм инвалидации:

По хешу содержимого файла
При изменении файла → новый хэш → cache miss
Автоматическая инвалидация
TTL (Time To Live):

Рекомендуемый: 90-180 дней
Обоснование: Файлы редко меняются после загрузки
Текущий: 30 дней (можно увеличить)
Формат хранения:

Текущий: JSONL (JSON Lines)
Рекомендуемый: JSONL или SQLite для индексации
Оценка эффективности:

Cache hit rate: 70-90% (при повторной обработке)
Экономия времени: 1-5 секунд на документ
ROI: ОЧЕНЬ ВЫСОКИЙ
1.2 LLM ответы ✅ ВЫСОКИЙ ПРИОРИТЕТ
Описание: Ответы от языковых моделей (OpenRouter, Groq, Replicate)

Критерии кэшируемости:

✅ Детерминированный промпт → предсказуемый ответ
✅ ОЧЕНЬ дорогая операция (токены + время)
✅ Высокая частота одинаковых запросов
⚠️ Может быть недетерминированным при temperature > 0
Ключ кэша:

# Текущая реализация
cache_data = {
    'prompt': prompt,
    'kwargs': {k: v for k, v in kwargs.items() if k not in ['stream', 'callback']}
}
key = MD5(json.dumps(cache_data, sort_keys=True))
Механизм инвалидации:

По хешу промпта + параметров
Исключаются параметры: stream, callback
Учитываются: temperature, max_tokens, model
TTL (Time To Live):

Рекомендуемый: 30-90 дней
Обоснование: Промпты меняются реже, чем данные
Текущий: 1 час (3600 секунд) - СЛИШКОМ КОРОТКИЙ
Формат хранения:

Текущий: Двухуровневый (Memory + File)
Memory: LRU cache (100 элементов)
File: JSON файлы в структурированных директориях
Сжатие: Ответы >100KB сжимаются gzip
Оценка эффективности:

Cache hit rate: 40-60% (зависит от разнообразия промптов)
Экономия: $0.001-0.01 на запрос + 1-3 секунды
ROI: ОЧЕНЬ ВЫСОКИЙ
Рекомендации:

⚠️ Увеличить TTL до 30-90 дней
✅ Добавить версионирование промптов
✅ Мониторить cache hit rate
1.3 Структурный анализ PDF ✅ СРЕДНИЙ ПРИОРИТЕТ
Описание: Анализ структуры PDF (наличие текстового слоя, шрифты, объекты)

Критерии кэшируемости:

✅ Детерминированный результат
✅ Относительно дорогая операция (1-3 секунды)
✅ Стабильный результат
✅ Используется для принятия решений об OCR
Ключ кэша:

# Текущая реализация
cache_data = f"{pdf_path.name}_{stat.st_size}_{stat.st_mtime}"
key = MD5(cache_data)
Кэшируемые данные:

{
    'has_text_layer': bool,

    'has_embedded_fonts': bool,
    'text_objects_count': int,
    'image_objects_count': int,
    'font_types': set,
    'text_confidence': float,
    'structure_score': float,
    'page_count': int
}
TTL:

Рекомендуемый: 180-365 дней
Обоснование: Структура PDF не меняется
Текущий: Бессрочно (нет TTL)
Оценка эффективности:

Cache hit rate: 80-95%
Экономия времени: 1-3 секунды на документ
ROI: ВЫСОКИЙ

Описание: Найденные ИНН организаций через DaData/ФНС

Критерии кэшируемости:

✅ Относительно стабильные данные
✅ Дорогая операция (API запросы)
⚠️ Данные могут устаревать (организация закрылась)
✅ Высокая частота повторных запросов

{

TTL:

Рекомендуемый: 90-180 дней
Обоснование: ИНН меняются редко, но возможны изменения
Текущий: 180 дней ✅
Механизм инвалидации:

По TTL (автоматическая очистка)
Ручная инвалидация при обнаружении ошибок
Оценка эффективности:

Cache hit rate: 60-80%
Экономия: API запросы + 0.5-2 секунды
ROI: ВЫСОКИЙ

Критерии кэшируемости:

⚠️ Результат может меняться (email может стать невалидным)
✅ Относительно дорогая операция (SMTP проверка)
⚠️ Низкая стабильность результата

Рекомендуемый: 7-30 дней
Обоснование: Email может стать невалидным
Оценка эффективности:

Экономия: SMTP проверка (1-3 секунды)
ROI: СРЕДНИЙ

2. Процессы, которые НЕЛЬЗЯ кэшировать
2.1 Загрузка писем из IMAP ❌ НЕ КЭШИРОВАТЬ
Описание: Получение новых писем с почтового сервера

Причины НЕ кэшировать:

❌ Данные постоянно меняются (новые письма)
❌ Цель - получить АКТУАЛЬНЫЕ данные
❌ Кэширование противоречит бизнес-логике
❌ Каждый запрос должен проверять новые письма
Альтернативы:

✅ Кэшировать метаданные писем (заголовки)
✅ Кэшировать список обработанных писем (чтобы не обрабатывать дважды)
✅ Использовать инкрементальную синхронизацию
2.2 Текущее время и даты ❌ НЕ КЭШИРОВАТЬ
Описание: Получение текущего времени, дат, timestamps

Причины НЕ кэшировать:

❌ Данные меняются каждую секунду
❌ Кэширование приведет к неправильным результатам
❌ Операция очень быстрая (не требует оптимизации)
2.3 Случайные значения ❌ НЕ КЭШИРОВАТЬ
Описание: Генерация UUID, случайных чисел

Причины НЕ кэшировать:

❌ Недетерминированный результат
❌ Кэширование нарушит уникальность
❌ Операция очень быстрая
2.4 Результаты с высокой динамикой ❌ НЕ КЭШИРОВАТЬ
Описание: Курсы валют, цены, статусы в реальном времени

Причины НЕ кэшировать:

❌ Данные меняются часто
❌ Требуется актуальность
⚠️ Можно кэшировать с ОЧЕНЬ КОРОТКИМ TTL (минуты)
2.5 Пользовательские сессии ❌ НЕ КЭШИРОВАТЬ (или с осторожностью)
Описание: Данные активных сессий пользователей

Причины НЕ кэшировать:

❌ Высокая динамика изменений
❌ Требования безопасности
⚠️ Можно использовать Redis с коротким TTL
2.6 Результаты с побочными эффектами ❌ НЕ КЭШИРОВАТЬ
Описание: Операции записи в БД, отправка email, платежи

Причины НЕ кэшировать:

❌ Имеют побочные эффекты
❌ Должны выполняться каждый раз
❌ Кэширование приведет к потере данных

4. Критерии кэшируемости (общие правила)
✅ Процесс МОЖНО кэшировать, если:
Детерминированность: Одинаковый вход → одинаковый выход
Стабильность: Результат не меняется часто
Дороговизна: Операция занимает значительное время/ресурсы
Частота повторов: Одинаковые запросы повторяются часто
Без побочных эффектов: Операция только читает данные
Идемпотентность: Можно вызывать многократно без изменения состояния
❌ Процесс НЕЛЬЗЯ кэшировать, если:
Недетерминированность: Результат зависит от случайности/времени
Высокая динамика: Данные меняются очень часто
Побочные эффекты: Операция изменяет состояние системы
Требование актуальности: Нужны самые свежие данные
Безопасность: Кэширование создает риски безопасности
Уникальность: Результат должен быть уникальным каждый раз
5. Рекомендации по реализации кэширования
5.1 Архитектура кэша
Многоуровневая система:

Level 1: In-Memory Cache (LRU)
    ↓ miss
Level 2: Local File Cache (JSONL/SQLite)
    ↓ miss
Level 3: Distributed Cache (Redis) [опционально]
    ↓ miss
Original Source (OCR/LLM/API)
5.2 Ключевые метрики для мониторинга
cache_metrics = {
    'total_requests': int,
    'cache_hits': int,
    'cache_misses': int,
    'cache_hit_rate': float,  # hits / total
    'avg_hit_latency': float,  # мс
    'avg_miss_latency': float,  # мс
    'cache_size': int,  # bytes
    'evictions': int,  # количество вытесненных записей
}
5.3 Стратегии инвалидации
TTL (Time To Live) - автоматическое истечение
LRU (Least Recently Used) - вытеснение редко используемых
Explicit invalidation - ручная инвалидация
Version-based - инвалидация по версии данных
Event-based - инвалидация по событиям
5.4 Оптимизация производительности
Для OCR:

Использовать SHA256 хеш содержимого файла
Сжимать большие тексты (>100KB)
Индексировать по хешу для быстрого поиска
Для LLM:

Увеличить TTL до 30-90 дней
Добавить версионирование промптов
Использовать семантическое кэширование (похожие промпты)
Для ИНН:

Добавить проверку актуальности через API раз в N дней
Кэшировать отрицательные результаты отдельно (короткий TTL)

8. Выводы
Ключевые находки:
OCR и LLM - самые важные кандидаты для кэширования (высокий ROI)
Текущий LLM TTL слишком короткий - нужно увеличить с 1 часа до 30-90 дней

ИНН: Экономия API запросов × 60-80% hit rate = хорошая экономия
Общий эффект: Ускорение обработки в 2-5 раз при правильной настройке кэширования
