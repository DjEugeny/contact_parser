# Design — Simplified Strategy Phone Sanitizer Fix

## Контекст
- Последний прогон `api_pipeline_validator.py` (лог: `data/logs/api_pipeline_validator_20251001_215602_unknown.log`) показал стабильную работу основной стратегии, но повторная обработка письма `email_016_20250729_20250729_dna-technology_ru_6360137e.json` упала на шаге `simplified` с ошибкой `expected string or bytes-like object, got 'int'`.
- Ошибка возникает после успешной валидации JSON и постпроцессинга: основной проход отдаёт 3 контакта / 3 организации, но при переходе к упрощённой стратегии обработчик падает внутри `process_single_email` → `PostProcessor` → `DataNormalizer`, где `re.sub` получает числовое значение вместо строки.
- Санитайзер (`LLMResponseValidator._sanitize_response`) уже объединяет структуры, однако не нормализует типы значений внутри вложенных объектов (например, `contacts[].phones[].number`). При вводе LLM числовых значений (без кавычек) они проходят в пайплайн как `int`.

## Гипотеза
- В ответе LLM телефонные поля (или другие строковые поля) пришли как числа. На стандартном пути это не приводит к аварии, потому что PostProcessor обрабатывает данные без повторной постобработки. В `simplified` после вызова `fix_none_values_in_data` → `sanitize_json_fields` → `fix_json_schema_validation_errors` значения остаются `int` и затем попадают в `DataNormalizer._simple_phone_cleanup`, где используется `re.sub`, требующий строку. Поэтому exception повторяется на каждой попытке.

## Цель
- Гарантировать, что санитайзер приводит строковые поля (особенно в телефонных структурах) к строковым типам до передачи в постпроцессор, чтобы любые стратегии (`standard`, `simplified`, `fallback`) работали с единообразными данными.

## Ключевые изменения
1. **Улучшение санитайзера (`src/core/validator.py`)**
   - В `_sanitize_contact` и `_sanitize_organization` привести значения `number/formatted/normalized/original/extension`, `email`, `position`, `city`, `address`, `role_in_message` к строкам с обрезкой пробелов.
   - В `_sanitize_interaction` приводить `summary`, `message_subject`, `message_date`, `message_id_hint` к строкам; `attachments` уже конвертируются.
   - Для `commercial_offers.equipment_items` приводить `name`, `model`, `article`, `vat` в строки (они могут прийти числами).
2. **PostProcessor — дополнительная страховка**
   - Перед нормализацией конвертировать строки контактов и equipment items (если не строка) в `as_text`, чтобы основной путь и simplified имели одинаковую защиту.
3. **Диагностика**
   - Добавить логгер/метаданные, фиксирующие количество полей, приведённых из int → str, чтобы легче отслеживать такие случаи.
4. **Тесты**
   - Дополнить юнит-тесты санитайзера/постпроцессора кейсом, где телефон приходит как `89031234567` (int), и убедиться, что `PostProcessor` не падает, а номер становится строкой.

## Границы
- Не меняем `safe_math_utils` (оно только поверхностно обрабатывает значения).
- Изменения не затрагивают схему JSON; только предвалидационная нормализация.

## Риски и снижение
- **Риск**: агрессивная конверсия может затереть типы (например, `confidence`/`value_score`). → Конвертируем только заранее определённые строковые поля.
- **Риск**: рост объёма `removed_props`. → Мы не вырезаем поля, лишь нормализуем типы.
- **Риск**: повторное преобразование может скрыть ошибки LLM. → Логируем количество приведённых значений, чтобы при необходимости анализировать источник ошибок.

## Тест-план
- Юнит-тест для санитайзера (после `validate_llm_response` телефон int → строка).
- Юнит-тест для PostProcessor (контакт с `phone` = int не падает и создаёт нормализованный номер).
- Повторный прогон `api_pipeline_validator.py --mode first10` (особенно письмо `email_016...6360137e.json`).
