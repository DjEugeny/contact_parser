# Requirements Document

## Introduction

Данный документ описывает требования к функции обогащения телефонов контактов от связанных организаций. Цель — предоставить пользователям полную контактную информацию в UI, при этом избегая ошибочных обогащений и "шума" в данных.

В текущем пайплайне LLM часто присваивает телефоны организациям, даже когда они находятся рядом с конкретными контактами в исходном тексте. Это создает ситуацию, когда в UI карточка контакта выглядит неполной, хотя телефон организации может быть релевантен для этого контакта.

## Requirements

### Requirement 1: Безопасное обогащение телефонов контактов

**User Story:** Как пользователь системы, я хочу видеть телефоны организации в карточке контакта, чтобы иметь возможность связаться с ним, даже если LLM не присвоил телефон напрямую контакту.

#### Acceptance Criteria

1. WHEN контакт имеет пустой массив `phones: []` AND связанная организация имеет телефоны THEN система ДОЛЖНА рассмотреть возможность обогащения контакта телефонами организации

2. WHEN контакт уже имеет персональные телефоны (мобильные) THEN система НЕ ДОЛЖНА добавлять офисные телефоны организации автоматически

3. WHEN контакт связан с организацией через `organization_id` AND организация имеет телефоны типа "main" или "office" THEN система ДОЛЖНА добавить эти телефоны контакту с метаданными об источнике

4. IF телефон организации имеет тип "mobile" THEN система НЕ ДОЛЖНА копировать его контакту (высокий риск ошибки)

5. WHEN система обогащает контакт телефоном организации THEN она ДОЛЖНА добавить метаданные: `source: "org_enrichment"`, `org_gid: "<organization_gid>"`, `confidence: <score>`

### Requirement 2: Оценка уверенности обогащения

**User Story:** Как разработчик системы, я хочу иметь систему scoring для оценки уверенности в обогащении, чтобы минимизировать ложные обогащения.

#### Acceptance Criteria

1. WHEN контакт имеет корпоративный email с доменом организации THEN confidence += 0.3

2. WHEN контакт имеет должность (position не null) THEN confidence += 0.2

3. WHEN контакт имеет role_in_message = "sender" или "recipient" THEN confidence += 0.2

4. WHEN контакт имеет city, совпадающий с city организации THEN confidence += 0.15

5. WHEN контакт имеет высокий value_score (≥ 7) THEN confidence += 0.15

6. IF итоговый confidence < 0.5 THEN система НЕ ДОЛЖНА обогащать контакт

7. IF итоговый confidence ≥ 0.5 AND < 0.75 THEN обогащение ДОЛЖНО быть помечено как "needs_review"

8. IF итоговый confidence ≥ 0.75 THEN обогащение ДОЛЖНО быть автоматически принято

### Requirement 3: Фильтрация типов телефонов

**User Story:** Как пользователь системы, я хочу получать только релевантные типы телефонов от организации, чтобы избежать дублирования личных номеров.

#### Acceptance Criteria

1. WHEN система обогащает контакт THEN она ДОЛЖНА копировать только телефоны типов: "main", "office", "fax"

2. WHEN организация имеет телефон типа "mobile" THEN система НЕ ДОЛЖНА копировать его контакту (риск персональных данных)

3. WHEN организация имеет несколько телефонов одного типа THEN система ДОЛЖНА копировать все релевантные телефоны

4. WHEN телефон организации не имеет типа (type = null) THEN система ДОЛЖНА обработать его как "main" с пониженным confidence (-0.1)

### Requirement 4: Предотвращение дублирования

**User Story:** Как пользователь системы, я хочу избежать дублирования телефонов в карточке контакта, чтобы данные были чистыми и читаемыми.

#### Acceptance Criteria

1. WHEN система добавляет телефон контакту THEN она ДОЛЖНА проверить наличие дубликатов по полю `normalized`

2. IF телефон с таким `normalized` уже существует у контакта THEN система НЕ ДОЛЖНА добавлять дубликат

3. WHEN контакт уже имеет телефон с `source: "llm"` AND система пытается добавить тот же телефон с `source: "org_enrichment"` THEN система ДОЛЖНА пропустить обогащение (LLM-источник приоритетнее)

4. WHEN система обнаруживает дубликат THEN она ДОЛЖНА логировать это событие в метаданные

### Requirement 5: Прозрачность и отслеживаемость

**User Story:** Как разработчик системы, я хочу иметь полную прозрачность процесса обогащения, чтобы отлаживать и улучшать алгоритм.

#### Acceptance Criteria

1. WHEN система обогащает контакт THEN она ДОЛЖНА сохранить метаданные в `postprocessing_metadata.contact_phone_enrichment`

2. WHEN обогащение выполнено THEN метаданные ДОЛЖНЫ содержать: `contact_gid`, `phones_added`, `phones_skipped`, `confidence_scores`, `decision_reason`

3. WHEN обогащение пропущено THEN метаданные ДОЛЖНЫ содержать причину: "low_confidence", "no_org_phones", "already_has_phones", "mobile_only"

4. WHEN система обрабатывает batch писем THEN она ДОЛЖНА собирать статистику: `contacts_enriched`, `phones_added_total`, `avg_confidence`

### Requirement 6: Интеграция с существующим пайплайном

**User Story:** Как разработчик системы, я хочу интегрировать обогащение телефонов в существующий пайплайн постобработки, чтобы не нарушить работу других модулей.

#### Acceptance Criteria

1. WHEN обогащение телефонов выполняется THEN оно ДОЛЖНО происходить ПОСЛЕ этапа "Разрешение конфликтов телефонов" (этап 9)

2. WHEN обогащение телефонов выполняется THEN оно ДОЛЖНО происходить ДО этапа "Нормализация данных" (этап 11)

3. WHEN обогащение добавляет телефоны THEN они ДОЛЖНЫ быть в формате phone object: `{type, number, normalized, original, extension}`

4. WHEN обогащение завершено THEN система ДОЛЖНА вызвать нормализацию для новых телефонов

5. IF обогащение вызывает ошибку THEN система ДОЛЖНА логировать ошибку и продолжить обработку без прерывания пайплайна

### Requirement 7: Конфигурируемость

**User Story:** Как администратор системы, я хочу иметь возможность настраивать параметры обогащения, чтобы адаптировать систему под специфику данных.

#### Acceptance Criteria

1. WHEN система инициализируется THEN она ДОЛЖНА загрузить конфигурацию из `config/settings.py`

2. WHEN конфигурация содержит `CONTACT_PHONE_ENRICHMENT_CONFIG.enabled = False` THEN система НЕ ДОЛЖНА выполнять обогащение

3. WHEN конфигурация содержит `min_confidence_threshold` THEN система ДОЛЖНА использовать это значение вместо дефолтного 0.5

4. WHEN конфигурация содержит `allowed_phone_types` THEN система ДОЛЖНА копировать только указанные типы телефонов

5. WHEN конфигурация содержит `enrichment_mode: "conservative"` THEN система ДОЛЖНА использовать повышенный порог confidence (0.75)

### Requirement 8: Обработка edge cases

**User Story:** Как разработчик системы, я хочу корректно обрабатывать граничные случаи, чтобы система была устойчивой к различным сценариям данных.

#### Acceptance Criteria

1. WHEN контакт не связан с организацией (organization_id = null) THEN система ДОЛЖНА пропустить обогащение

2. WHEN организация не найдена по organization_id THEN система ДОЛЖНА логировать предупреждение и пропустить контакт

3. WHEN организация имеет пустой массив phones THEN система ДОЛЖНА пропустить обогащение с причиной "no_org_phones"

4. WHEN телефон организации имеет normalized = null THEN система ДОЛЖНА пропустить этот телефон

5. WHEN контакт имеет phones = null (не массив) THEN система ДОЛЖНА инициализировать пустой массив перед обогащением

6. WHEN в процессе обогащения возникает исключение THEN система ДОЛЖНА логировать полный traceback и продолжить обработку следующего контакта
