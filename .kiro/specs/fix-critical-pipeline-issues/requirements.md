# Документ требований

## Введение

Данный документ описывает требования для исправления оставшихся критических проблем в пайплайне обработки электронной почты. После решения проблем с кэшированием и накоплением данных между письмами, остались три ключевые проблемы: неправильная обработка регистра в постобработке, отсутствие активного обогащения данных и ошибки валидации.

## Требования

### Требование 1: Сохранение правильного форматирования регистра

**Пользовательская история:** Как бизнес-пользователь, я хочу, чтобы названия организаций, должности и аббревиатуры сохраняли правильную капитализацию, чтобы извлеченные данные выглядели профессионально и точно.

#### Критерии приемки

1. КОГДА обрабатываются должности ТО система ДОЛЖНА нормализовать только первое слово с заглавной буквы, остальные слова как в исходном JSON
2. КОГДА обрабатываются названия организаций ТО система ДОЛЖНА нормализовать только первое слово с заглавной буквы, остальные слова как в исходном JSON
3. КОГДА встречаются аббревиатуры типа "КДЛ", "ОМТС", "ООО" ТО система ДОЛЖНА сохранить их в исходном регистре
4. КОГДА встречаются названия в кавычках ТО система ДОЛЖНА сохранить исходное форматирование внутри кавычек
5. КОГДА выполняется постобработка ТО система НЕ ДОЛЖНА применять .capitalize() или .title() ко всему тексту
6. КОГДА неуверенность в правильной капитализации ТО система ДОЛЖНА сохранить исходное форматирование из raw JSON

### Требование 2: Исправление логики обогащения данных

**Пользовательская история:** Как бизнес-пользователь, я хочу, чтобы обогащение контактов веб-сайтами работало корректно только для корпоративных email, исключая публичные провайдеры и предотвращая перекрестное обогащение между организациями.

#### Критерии приемки

1. КОГДА обрабатывается корпоративный email ТО система ДОЛЖНА обогатить контакт соответствующим веб-сайтом
2. КОГДА обрабатывается email с публичного провайдера (mail.ru, yandex.ru, gmail.com, bk.ru) ТО система НЕ ДОЛЖНА обогащать контакт веб-сайтом провайдера
3. КОГДА контакт принадлежит organization_id X ТО система НЕ ДОЛЖНА обогащать его сайтом от organization_id Y
4. КОГДА домен email совпадает с доменом организации контакта ТО система ДОЛЖНА применить обогащение
5. ЕСЛИ домен email не совпадает с организацией контакта ТО система НЕ ДОЛЖНА применять обогащение
6. КОГДА обогащение применяется ТО система ДОЛЖНА записать источник и причину обогащения в лог

### Требование 3: Обеспечение 100% стабильности обработки писем

**Пользовательская история:** Как системный оператор, я хочу, чтобы система обеспечивала 100% стабильный результат обработки писем без создания файлов с ошибками, автоматически повторно обрабатывая проблемные письма до получения валидного результата.

#### Критерии приемки

1. КОГДА обрабатывается любое письмо ТО система ДОЛЖНА производить валидный результат без ошибок
2. КОГДА возникает ошибка обработки ТО система НЕ ДОЛЖНА создавать файлы с ошибками в названии или содержании
3. КОГДА письмо не обработалось с первого раза ТО система ДОЛЖНА автоматически повторить обработку в том же запуске
4. КОГДА повторная обработка успешна ТО система ДОЛЖНА перезаписать проблемные артефакты валидными результатами
5. ЕСЛИ письмо не обрабатывается после нескольких попыток ТО система ДОЛЖНА применить fallback стратегию с базовой структурой данных
6. КОГДА запуск завершен ТО ВСЕ созданные файлы ДОЛЖНЫ содержать валидные данные без ошибок

### Требование 4: Обеспечение комплексного логирования и мониторинга

**Пользовательская история:** Как системный оператор, я хочу подробное логирование всех этапов обработки, чтобы я мог быстро выявлять и решать проблемы при их возникновении.

#### Критерии приемки

1. КОГДА обрабатываются письма ТО система ДОЛЖНА записывать каждый основной этап обработки с временными метками
2. КОГДА возникают ошибки ТО система ДОЛЖНА записывать подробную информацию об ошибке, включая контекст и потенциальные причины
3. КОГДА обрабатываются вложения ТО система ДОЛЖНА записывать результаты OCR и статус интеграции с LLM
4. КОГДА происходит обогащение данных ТО система ДОЛЖНА записывать попытки и результаты обогащения
5. КОГДА валидация не удается ТО система ДОЛЖНА записывать конкретные ошибки валидации с примерами
6. КОГДА обработка завершена ТО система ДОЛЖНА предоставить сводку успешных и неудачных операций
