# Анализ задачи TASK-008B: Contact Location Safety

## Обзор задачи

Задача направлена на предотвращение ложного обогащения контактов локационными данными (город/адрес) из блоков организации (HQ). Контакты должны получать локационные данные **только** при наличии явных персональных сигналов.

## Критический анализ текущего плана

### ✅ Сильные стороны плана

1. **Четкая проблема**: План ясно описывает проблему "протечки" HQ-данных в контакты
2. **Конкретные кейсы**: Есть реальные примеры (письма 016, 017) для воспроизведения
3. **Инварианты**: Четко определены правила, когда можно и нельзя заполнять локацию контакта
4. **Встраивание в пайплайн**: Понятно, где в существующем пайплайне должна работать логика
5. **Защита от регресса**: Предусмотрена защита от перезаписи существующих данных
6. **Тест-план**: Есть критерии приемки (DoD)

### ⚠️ Потенциальные проблемы и улучшения

#### 1. Недостаточная детализация эвристик
**Проблема**: Эвристики разделения персонального и HQ-блока описаны поверхностно.

**Предложение**: 
- Добавить приоритизацию сигналов (сильные vs слабые)
- Определить, что делать при конфликтующих сигналах
- Уточнить обработку случаев, когда контакт является руководителем (его локация может совпадать с HQ)

#### 2. Неясность с "внутренними сотрудниками"
**Проблема**: Упоминается "домен нашей компании", но не определено, как его идентифицировать.

**Предложение**: 
- Определить механизм идентификации внутренних сотрудников
- Уточнить, нужна ли конфигурация для списка внутренних доменов

#### 3. Отсутствие обработки edge cases
**Проблема**: Не описаны граничные случаи:
- Контакт работает удаленно из другого города
- Несколько офисов организации в разных городах
- Контакт упоминает несколько городов в подписи

**Предложение**: Добавить правила для этих случаев

#### 4. Confidence scoring не детализирован
**Проблема**: Упоминается `confidence` в Evidence, но не описано, как его вычислять.

**Предложение**: 
- Определить шкалу confidence (0.0-1.0)
- Описать факторы, влияющие на confidence
- Установить минимальный порог для применения данных

#### 5. Метаданные и отладка
**Проблема**: Структура `postprocessing_metadata.location_evidence` не полностью определена.

**Предложение**: 
- Добавить поля для отладки: `rejected_reason`, `source_type`, `matched_patterns`
- Сохранять информацию о том, почему данные НЕ были применены

location_safety = ContactLocationSafety()
evidence_map = location_safety.extract_contact_location_evidence(
    message, signature_blocks
)

for contact in contacts:
    evidence = evidence_map.get(contact['gid'])
    if evidence and evidence.confidence >= MIN_CONFIDENCE:
        applied = location_safety.apply_contact_location(
            contact, evidence, metadata
        )
