✅ Summary - Phone Extension Normalization Issue Fixed
I have successfully identified and fixed the phone normalization issue that was causing incorrect phone number storage for organizations after LLM processing. Here's what was wrong and what I fixed:
🚨 The Problems Identified:
JSON Schema Validation Issue: The validator expected organizations.phones to be an array of strings, but the system was trying to process phone objects with extensions.
Phone Normalization "Concatenation" Bug: The PhoneNormalizer.normalize_contact_phone() method was adding extensions back into the formatted field, creating malformed concatenated phone numbers like "74959337147749593371477495933714748171 (доб. 171)".
Data Structure Inconsistency: LLM was returning correct phone objects, but postprocessing was corrupting them by re-adding extensions to the number field.
🔧 The Fixes Applied:
1. Updated JSON Schema Validator (src/core/validator.py)
Changed organization phones schema from array of strings to array of phone objects
Now accepts phones: [object] with fields: {type, number, normalized, original, extension}
2. Fixed PhoneNormalizer Extension Handling (src/postprocessing/phone_normalizer.py)
CRITICAL FIX: Removed the code that was adding extensions back to the formatted phone number
Extensions now stay only in the separate extension field
Added new method normalize_phone_to_object() that returns proper phone objects
3. Enhanced Data Normalizer (src/postprocessing/data_normalizer.py)
Updated _normalize_phone_entry() to use the new phone normalization approach
Better handling of phone objects vs strings from LLM
Graceful degradation with fallback normalization
4. Fixed Validator Sanitizer (src/core/validator.py)
Updated organization phone sanitizer to handle both string and object phone formats
Maintains backward compatibility while supporting new structure

🎯 Key Achievements:
✅ Extension Separation: Extensions are now never included in the number or normalized fields
✅ Proper E.164 Format: Normalized numbers are in correct E.164 format without extensions
✅ Multiple Phone Support: Correctly handles compound phones like "(47)(48)"
✅ Schema Compliance: JSON validation now passes for phone objects
✅ Backward Compatibility: Supports both old string format and new object format
🔒 The Fix Ensures:
number field: Clean UI format WITHOUT extension (e.g., "+7 (495) 933-71-47")
normalized field: E.164 format WITHOUT extension (e.g., "+74959337147")
extension field: Only contains the extension digits (e.g., "171") or null
original field: Preserves the exact input string as received
This fix resolves the reported issue where phone numbers were being corrupted during postprocessing, ensuring that LLM's correct phone data is preserved and properly structured throughout the validation pipeline.
