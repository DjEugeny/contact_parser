# Requirements: Нормализация телефонов с добавочными номерами

## Введение

**Проблема**: телефоны с добавочными номерами типа `+7 (495) 933 71 47 (48), доб.171` неправильно парсятся, создавая дубликаты, что приводит к ошибкам JSON Schema валидации.

**Цель**: реализовать корректную нормализацию телефонов с чёткими правилами разделения базового номера и добавочного.

---

## Функциональные требования

### FR-1: Парсинг добавочных номеров

**Приоритет**: P0 (критический)

**Описание**: Система должна корректно извлекать добавочные номера из любых форм записи.

**Поддерживаемые форматы**:
- Русские: `доб.`, `доб:`, `доб`, `доп.`, `доп:`, `вн.`, `в.н.`, `внутр.`
- Английские: `ext`, `ext.`, `extension`, `x` (как отдельный префикс)
- В скобках: `(доб. 171)`, `(ext 45)`
- Смешанные: `доб. номер 101`

**Примеры**:
```
Вход: "+7 (495) 640-17-71 (доб. 2026)"
Выход: 
  - number: "+7 (495) 640-17-71"
  - extension: "2026"

Вход: "8(495)980-45-55, доб.1150"
Выход:
  - number: "+7 (495) 980-45-55"
  - extension: "1150"
```

**Правила**:
- Брать только цифры из добавочного: `[0-9]{1,10}`
- Если несколько меток — брать последнюю (самую правую)
- Удалять весь хвост с добавочным из базового номера

---

### FR-2: Парсинг множественных номеров

**Приоритет**: P0 (критический)

**Описание**: Корректно распознавать случаи, когда в строке указаны два номера через сокращённую форму.

**Примеры**:
```
Вход: "+7 (495) 933 71 47 (48), доб.171"
Распознать как:
  1. Базовый: +7 (495) 933-71-47
  2. Второй: +7 (495) 933-71-48 (последние 2 цифры заменены)
  
Оба с extension: "171"
```

**Паттерн**: `<базовый номер> (<N цифр>)`, где N < длины базового номера

**Алгоритм**:
1. Извлечь базовый номер до последних скобок
2. Извлечь цифры в скобках
3. Заменить последние N цифр базового на цифры из скобок
4. Применить добавочный к обоим номерам

---

### FR-3: Нормализация базового номера

**Приоритет**: P0 (критический)

**Описание**: Базовый номер нормализуется в E.164 формат **без** добавочного.

**Требования**:
- Использовать библиотеку `phonenumbers`
- Default region: `RU`
- Формат `normalized`: E.164 (`+74956401771`)
- Формат `number` (UI): `+7 (XXX) XXX-XX-XX` для RU, international для других

**Валидация**:
- Проверка `is_valid_number()`
- Если не валиден: `normalized = null`, `number` = очищенный без добавочного

---

### FR-4: Структура данных

**Приоритет**: P0 (критический)

**Описание**: Каждый телефон представлен объектом с фиксированным набором полей.

**Схема**:
```json
{
  "type": "mobile | office | fax | main | other | null",
  "number": "<UI вид без добавочного>",
  "normalized": "<E.164 или null>",
  "original": "<как пришло от LLM>",
  "extension": "<цифры добавочного или null>"
}
```

**Ограничения**:
- `number` **НИКОГДА** не содержит добавочный
- `normalized` **НИКОГДА** не содержит добавочный
- `extension` содержит **ТОЛЬКО** цифры (без префиксов типа "доб.")
- `original` сохраняет полную исходную строку

---

### FR-5: Дедупликация

**Приоритет**: P1 (высокий)

**Описание**: Уникальность телефонов проверяется по ключу `(normalized, extension, type)` в пределах одного контакта/организации.

**Правила**:
- Два телефона с одинаковым `normalized` и `extension`, но разным `type` — разные записи
- Два телефона с одинаковым `normalized` и `type`, но разным `extension` — разные записи
- Полные дубликаты — объединяются, сохраняется самый информативный `original`

---

## Нефункциональные требования

### NFR-1: Обратная совместимость

**Приоритет**: P1 (высокий)

**Описание**: Система должна обрабатывать телефоны как в старом (строки), так и в новом (объекты) формате.

**Требования**:
- Validator автоматически конвертирует строки в объекты
- PhoneNormalizer принимает оба формата на вход
- PostProcessor нормализует перед валидацией

---

### NFR-2: Производительность

**Приоритет**: P2 (средний)

**Описание**: Нормализация не должна существенно замедлять обработку.

**Требования**:
- Обработка одного номера < 10ms
- Batch обработка 100 номеров < 500ms
- Без блокировки других этапов пайплайна

---

### NFR-3: Логирование и отладка

**Приоритет**: P1 (высокий)

**Описание**: Детальное логирование процесса нормализации.

**Требования**:
- В `postprocessing_metadata.phone_normalization`:
  ```json
  {
    "processed": 15,
    "extensions_found": 8,
    "multiple_phones_split": 2,
    "validation_errors": 0,
    "examples": [
      {
        "original": "+7 (495) 933 71 47 (48), доб.171",
        "result_count": 2,
        "extension": "171"
      }
    ]
  }
  ```

## Валидация требований

### Критерии приёмки

1. **Парсинг добавочных**:
   - ✅ Все форматы из FR-1 распознаются
   - ✅ Добавочный извлекается корректно
   - ✅ Базовый номер очищается от добавочного

2. **Множественные номера**:
   - ✅ Паттерн `X (YY)` распознаётся как два номера
   - ✅ Добавочный применяется к обоим
   - ✅ Не создаются дубликаты

3. **Нормализация**:
   - ✅ `number` не содержит добавочный
   - ✅ `normalized` в E.164 без добавочного
   - ✅ `extension` только цифры
   - ✅ `original` сохранён полностью

4. **JSON Schema**:
   - ✅ Валидация проходит для объектов phones
   - ✅ uniqueItems работает по правильному ключу
   - ✅ Старые строковые phones автоконвертируются

5. **Интеграция**:
   - ✅ email_014 и email_015 обрабатываются успешно
   - ✅ Нет ошибок `non-unique elements`
   - ✅ Метаданные заполнены

**НЕ входит в эту задачу**:

- Валидация корректности добавочных номеров (существуют ли они)
- UI для отображения телефонов — фронтенд
