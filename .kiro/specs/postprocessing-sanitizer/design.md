# Design Document — Postprocessing Sanitizer & Resilient Backfill

## Контекст
- План **PLAN-002_Postprocessing_Refactor_and_Universal_Sanitizer_v2.md** фиксирует повторяющиеся падения валидации: LLM добавляет неожиданные поля (`confidence` на организациях), а fallback-ветка ломается на `re.sub` для числовых значений.
- Цель: стабилизировать весь постпроцессинг независимо от качества ответа модели, обеспечить управляемый backfill и телеметрию.

## Ключевые изменения архитектуры
1. **Промпт**: минимальный guardrail, запрещающий `confidence` для организаций. Изменения ограничены файлом `prompts/unified_contact_extraction_structured.txt`.
2. **Sanitize-слой в валидаторе**:
   - Новый модуль/функция `sanitize_payload` в `src/core/validator.py`.
   - Белые списки ключей по уровням (`root`, `organizations`, `contacts`, `commercial_offers`, `interactions`, вложенные массивы).
   - Санитайзер вставляет сведения о вычищенных полях в `postprocessing_metadata.sanitizer.removed_props`, включая путь, ключ и безопасный `value_preview` (обрезанный, либо `<redacted>` для чувствительных/больших структур).
   - Дополнительно приводит строковые/телефонные поля (организации, контакты, interactions, КП) к строковому типу, увеличивая счётчик `converted_to_string` для телеметрии.
   - Метаданные (`postprocessing_metadata`) не трогаем, чтобы не ломать отчётность.
3. **Утилиты нормализации в постпроцессоре** (`src/postprocessing/postprocessor.py`):
   - Ввод функций `as_text`, `as_int`, `as_float`, `as_bool`, `as_list`, `coerce_phone_list`, `safe_regex_sub`.
   - Central place для enum/date/price нормализации.
   - Корректное преобразование скаляров в списки (например, `attachments`).
4. **Backfill и provenance**:
   - Поддерживаем мягкий backfill города/адреса контактов (только если поля пустые).
   - Источники фиксируем в `postprocessing_metadata.provenance.contacts`.
5. **Fallback-цепочка** (`resilient_processor`, постпроцессор):
   - Все вызовы regex и преобразований проходят через безопасные утилиты.
   - Исключения логируются и попадают в метаданные, а не ломают пайплайн.
6. **Телеметрия**:
   - Расширяем `diagnostic_enricher` для отчётов по удалённым полям, автокоррекциям и backfill-кам.

## Поток обработки
```
Extractor → PostProcessor (dedup/enrich/filter → sanitize-friendly структуры) → Validator.sanitize_payload → JSON Schema → финальные артефакты/БД
```
- Sanitizer вызывается внутри `validator.validate_and_correct` до схемы и автокоррекции.
- PostProcessor использует новые утилиты для очистки данных до попадания в валидатор.

## Влияние на остальные компоненты
- `organization_deduplicator`, `smart_contact_enricher` — интерфейсы сохраняются.
- Артефакты отчётов: в `ReportGenerator` дополнительно отображаем очищенные поля (по желанию).
- Версия процессинга повышается (например, `1.3.0`) для отслеживания изменений.

## Риски и смягчение
- **Риск:** Санитайзер может удалить нужные поля, если whitelist неполный. → Покрываем автотестами, добавляем подробный лог в `removed_props` с коротким `value_preview` (или маркером для чувствительных данных).
- **Риск:** Новые вспомогательные функции могут повлиять на существующую нормализацию. → Пошаговое внедрение, регрессия на проблемных файлах и smoke-пакете.
- **Риск:** Пересчёт цен в `commercial_offers` может привести к расхождениям. → Сохраняем оригинальные значения в метаданных и описываем правила.

## Тестовый план (высокоуровневый)
- Юнит-тесты для `sanitize_payload` (разные уровни вложенности, удаление лишних ключей, нетронутые метаданные).
- Юнит/интеграция для новых утилит в постпроцессоре (конверсия типов, безопасные regex, enum/date/price normalization).
- Регресс на двух проблемных письмах (023/024) + smoke на мини-пакете 5 писем.
- Проверка provenance: контакт без города получает `org.city`, контакт с уже указанным городом — остаётся неизменным.

## Открытые вопросы
- Нужно ли хранить удалённые значения (например, `confidence`) отдельно для отладки или достаточно указать путь/ключ? (предлагаю ограничиться путём + ключом, как в плане).
- Нужна ли обратная совместимость с «старым» форматом `postprocessing_metadata`? (пока да: добавляем новые поля, не переименовывая старые).
