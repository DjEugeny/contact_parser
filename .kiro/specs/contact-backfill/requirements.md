# Документ требований

## Введение

Цель: исключить попадание адреса головного офиса в карточки персональных контактов и предоставить контролируемый механизм мягкого обогащения города/адреса из организации. Требуется сохранить строгую схему контактов и сделать происхождение данных прозрачным в `postprocessing_metadata`.

## Требования

### Требование 1: Корректность извлечённых персональных атрибутов
- LLM не должен копировать HQ-адрес/город из организационной подписи в персональные поля.
- Истинные упоминания города в тексте письма должны сохраняться (пример: «Региональный представитель … г. Новосибирск» → город контакта «Новосибирск»).

### Требование 2: Управляемый backfill
- В `PostProcessor` реализовать флаги `backfill_city_from_org` (по умолчанию `True`) и `backfill_address_from_org` (по умолчанию `False`).
- Мягкий бэкфилл заполняет `city` / `address` контакта только если поле пустое и в организации есть соответствующее значение.
- Уже извлечённые значения не перезаписываются.
- Происхождение сохранено в `postprocessing_metadata.provenance.contacts[contact_id]`.

### Требование 3: Прозрачность для UI
- UI-документ должен содержать требование отображать бейдж источника («из организации») рядом с городом/адресом, если поле заполнено бэкфиллом.
- Пользователь должен понимать, что значение пришло из организации, а не из письма.

### Требование 4: Обратная совместимость
- JSON Schema контактов не изменяется (запрещены новые поля).
- Все существующие тесты и валидация должны проходить без модификации схем.

### Требование 5: Тестовые сценарии
- А: Org.city заполнен, contact.city пустой → контакт получает город, provenance фиксируется.
- B: Org.city заполнен, contact.city заполнен → поле не перезаписывается, provenance отсутствует.
- C: Адрес по умолчанию не наследуется (флаг `False`).
- D: При включении адресного флага HQ-адрес подставляется только в пустое поле, provenance фиксируется.
- E: `postprocessing_metadata.provenance.contacts` присутствует только при срабатывании бэкфилла.
