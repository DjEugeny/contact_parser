
# TASK-008A: Attachment Evidence → Org City/Address (без правок промпта)

**Цель:**
- Обогащать `organizations.city` и `organizations.address` из **реальных вложений** (КП/бланки/реквизиты), не полагаясь на LLM. Контакты не трогаем (см. TASK-008B).
- Зафиксировать, что **источником локации для организаций** являются **реальные вложения**, уже распознанные OCR `.txt`, и внедрить «слой доказательств» до обогащения.
- Исключить зависимость от промпта LLM для этого аспекта: если LLM не подтянула город/адрес из КП, мы достанем его из OCR‑текста.

## Преамбула проблемы
В текущем пайплайне `organizations.city/address` заполняются не всегда корректно: **организации не обогащаются из вложений**, даже когда во вложениях (КП/реквизиты) явно указан город/адрес. При этом **контакты иногда получают HQ‑адрес/город** организации как будто это их персональные данные (этот аспект закрывается в TASK‑008B).

## Источник текстов вложений (важно)

AttachmentEvidenceExtractor читает **только нормализованный текст**, который уже подготовил `ocr_processor.py`:
- `attachment.text_content` (строка) **или**
- `attachment.text_path` (путь к `.txt`, где лежит распознанный текст из PDF/сканов/изображений).

Мы **не** открываем бинарные PDF/JPG/TIFF — все такие файлы предварительно превращаются в `.txt` OCR-модулем.

Минимальные метаданные вложения:
```json
{
  "filename": "Ком.пред...МИЛЛАБ....txt",
  "mime": "text/plain",
  "text_path": "/.../Ком.пред...МИЛЛАБ....txt",
  "sha1": "…",
  "size": 12345,
  "origin_mime": "application/pdf"
}
```

Преимущества подхода: единый текстовый интерфейс, отсутствие PDF-зависимостей, одинаковая логика для PDF/изображений/RTF, детерминированный парсинг.

## 1) Вход/выход

### Вход
- `email_data.attachments[]` с полями (минимум):  
  `filename, mime, text_content (string) | pages_text (list[str]), size, sha1`.

### Выход
- `evidence_index` — список объектов «доказательство локации для организации»:
```json
{
  "org_name_norm": "миллаб",         // нормализованное имя из вложения
  "matched_name": "ООО «МИЛЛАБ»",    // как встретилось в тексте
  "city": "Москва",                  // может быть null, если нашли только адрес без города
  "address": "117... г. Москва ...", // может быть null
  "source": {
    "type": "attachment",
    "filename": "Ком.пред....txt",
    "snippet": "… Адрес: 117… г. Москва …",
    "offset": 842
  },
  "confidence": 0.9
}
```

## 2) Алгоритм `attachment_evidence.extract()`

1. **Классификация вложений (простая):**
   - По имени файла (регистронезависимо): содержит `коммерчес`, `кп`, `реквизит`, `счет`, `договор`, `bill`, `invoice`, `offer` — **включаем** в поиск.
   - По «сигнатурам» текста: встречаются `ИНН`, `ОГРН`, `ООО`, `АО`, `Коммерческое предложение`, `Реквизиты` — **включаем**.

2. **Нормализация названий организаций:**
   - Снять юр. форму (`ООО`, `АО`, `ПАО`, `ФБУЗ`, и т.п.), кавычки‑ёлочки, регистр, сжать пробелы.
   - Результат — `org_name_norm`.

3. **Матч названия в тексте вложения:**
   - Ищем точные вхождения и fuzzy‑совпадения (допуск 0.9 по ratio).  
   - Для каждого совпадения ищем ближайшие строки с маркерами локации.

4. **Извлечение локации:**
   - Паттерны города: `\bг\.?\s+([А-ЯЁ][а-яё\-\s]+)`, `город\s+([А-ЯЁ][а-яё\-\s]+)`.
   - Паттерны адреса: `Адрес[:\s]+(.{10,140})` (обрезать по разделителям), `\b\d{6},\s+[^\n]+` (индекс‑регион‑город).
   - Нормализуем пробелы, удаляем хвосты «тел.», «e‑mail» и т.д.

5. **Сборка evidence:** как в «Выход»; `confidence` повышать, если совпали **и** название, **и** реквизиты (ИНН/ОГРН), **и** домен письма.

6. Вернуть `evidence_index` (список).

---

## 3) Алгоритм `org_location_enrichment()`

Для каждой `organization` после `assign gid`:
1. Собрать кандидаты из `evidence_index` по:
   - `org_name_norm` ≈ нормализованному названию карточки (ratio ≥ 0.9);  
   - либо по совпадению e2LD домена (если нашли в тексте e‑mail с доменом организации).

2. **Заполнение:**
   - Если `org.city is null` и в лучшем evidence есть `city` → записать `org.city`.
   - Если `org.address is null` и в лучшем evidence есть `address` → записать `org.address`.
   - **Никогда не перезаписывать** уже заполненные поля.

3. **Метаданные:**
   - В `postprocessing_metadata.location_evidence[org_gid]` добавить:
     ```json
     {"applied": true, "city": "...", "address": "...", "source": {...}, "confidence": 0.9}
     ```

4. **Конфликты:**
   - Если найдено несколько разных городов — не заполнять, `applied=false`, `needs_review=true` в метаданные.

## 4) Конфигурация (пример)

```yaml
attachment_evidence:

  filename_include_patterns: ["коммерчес", "кп", "реквизит", "счет", "договор", "offer", "invoice", "bill"]

  enabled: true

  prefer_fields: ["city","address"]
  log_metadata: true
```
