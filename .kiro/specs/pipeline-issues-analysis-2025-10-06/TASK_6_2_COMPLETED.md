Файл `prompts/unified_contact_extraction_v1.1.txt` создан на основе v1.0 с существенными улучшениями.

#### 1.1 Добавлены строгие правила для null значений

```
🚨 **СТРОГИЕ ПРАВИЛА ДЛЯ ОБЯЗАТЕЛЬНЫХ ПОЛЕЙ:**
- ❌ **НИКОГДА не используй `null` для обязательных ID полей:**
  - `contact_id` - ВСЕГДА число (1, 2, 3...)
  - `organization_id` - ВСЕГДА число (1, 2, 3...)
  - `interaction_local_id` - ВСЕГДА число (1, 2, 3...)
- ❌ **НИКОГДА не используй `null` для обязательных строковых полей:**
  - `name` (для контактов и организаций) - ВСЕГДА строка
  - `interaction_type` - ВСЕГДА одно из допустимых значений enum
- ✅ **Используй `null` ТОЛЬКО для опциональных полей:**
  - `city`, `address`, `website`, `inn` - могут быть `null`
  - `extension` (для телефонов) - может быть `null`
  - `normalized` (для телефонов) - может быть `null`
```

✅ Решает проблему: `None is not of type 'integer'` для ID полей

#### 1.2 Добавлен полный список допустимых значений interaction_type

```
🎯 **ПРАВИЛА ДЛЯ ENUM ПОЛЕЙ:**
- `interaction_type` ДОЛЖЕН быть ТОЛЬКО одним из этих значений:
  - `"requested_quote"` - запрос коммерческого предложения
  - `"sent_quote"` - отправка коммерческого предложения
  - `"follow_up"` - напоминание, уточнение по предыдущему запросу
  - `"clarification"` - уточнение деталей, вопросы (НЕ "info_request"!)
  - `"complaint"` - жалоба, рекламация
  - `"invoice_sent"` - отправка счета
  - `"invoice_paid"` - оплата счета
  - `"contract_sent"` - отправка договора
  - `"contract_signed"` - подписание договора
  - `"delivery"` - доставка товара
  - `"support"` - техническая поддержка
  - `"other"` - другое взаимодействие
- ❌ **ЗАПРЕЩЕНО использовать:** `"info_request"` (используй `"clarification"` вместо этого)
- ❌ **ЗАПРЕЩЕНО придумывать свои значения** - только из списка выше!
```

✅ Решает проблему: `'info_request' is not one of [...]`

#### 1.3 Добавлены 3 примера правильного JSON

**Пример 1:** Простое письмо с запросом КП
- Демонстрирует правильную структуру базового запроса
- Показывает правильное использование ID полей
- Правильный `interaction_type: "requested_quote"`

**Пример 2:** Уточнение деталей (clarification вместо info_request)
- Демонстрирует правильное использование `"clarification"`
- Показывает как обрабатывать опциональные поля (null)
- Правильная структура для уточняющих вопросов

**Пример 3:** Обязательные связи между сущностями
- Демонстрирует правильные связи между contacts, organizations и interactions
- Показывает как каждый contact должен иметь organization_id
- Показывает как каждый interaction должен иметь contact_id И organization_id

✅ Решает проблему: LLM видит конкретные примеры правильного JSON

#### 1.4 Добавлены примеры неправильного JSON

```
## 🚫 ПРИМЕРЫ НЕПРАВИЛЬНОГО JSON (НЕ ДЕЛАЙ ТАК!)

### ❌ Ошибка 2: Неправильное значение enum
### ❌ Ошибка 3: Отсутствие обязательных связей
```

✅ Решает проблему: LLM видит что НЕ нужно делать

#### 1.5 Добавлена финальная проверка перед отправкой

```
## ✅ ФИНАЛЬНАЯ ПРОВЕРКА ПЕРЕД ОТПРАВКОЙ

Перед тем как вернуть JSON, проверь:

1. ✅ Все `contact_id`, `organization_id`, `interaction_local_id` - это ЧИСЛА (не null!)
2. ✅ Все `interaction_type` - только из допустимого списка (не "info_request"!)
3. ✅ Каждый контакт имеет `organization_id`
4. ✅ Каждое взаимодействие имеет `contact_id` И `organization_id`
5. ✅ Все ID ссылаются на существующие сущности
6. ✅ JSON валиден (правильные скобки, запятые, кавычки)
7. ✅ Нет лишних полей (например, `confidence` в `organizations`)

Если хотя бы одна проверка не прошла - исправь перед отправкой!
```

✅ Решает проблему: LLM проверяет себя перед отправкой
