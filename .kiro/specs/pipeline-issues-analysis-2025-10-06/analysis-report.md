## Выявленные проблемы

### 1. КРИТИЧЕСКАЯ: Неэффективная логика обработки OCR вложений

**Описание:**  
Pipeline запускает полный OCR модуль для каждого вложения, даже если файл уже обработан. OCR модуль инициализируется, сканирует папки, проверяет кэш и только потом возвращает "уже обработано".

**Детали:**
- Затронуто: ~12 писем с вложениями
- Избыточных запусков OCR модуля: 12
- Потеря времени: ~20-30 секунд на 30 писем
- Засорение логов избыточными сообщениями

**Текущая (неправильная) логика:**
```
1. Pipeline видит вложение
2. Запускает ВЕСЬ OCR модуль (инициализация, сканирование, кэш)
3. OCR модуль проверяет: "файл уже обработан?"
4. OCR модуль возвращает: "Пропускаю"
```

**Правильная логика:**
```
1. Pipeline проверяет наличие файла результата OCR в data/final_results/{filename}.json
2. Если файл результата ЕСТЬ → загружает текст из файла, пропускает OCR модуль
3. Если файла результата НЕТ → запускает OCR модуль для обработки файла
```

**Примечание о "кэше":**  
Термин "кэш" здесь означает двухуровневую систему:
- **In-memory кэш** (словарь в памяти) - для быстрого доступа к уже загруженным результатам
- **Файловый кэш** (data/final_results/) - постоянное хранилище результатов OCR

**Причина:**  
Нарушение принципа единственной ответственности. OCR модуль отвечает за проверку файлов результатов, хотя это должен делать Pipeline.

**Метод устранения:**
1. Создать OCRCacheManager в Pipeline для проверки файлов результатов
2. Реализовать ленивую инициализацию OCR модуля
3. Упростить OCR модуль - убрать проверки кэша
4. Добавить batch-проверку кэша для нескольких файлов
5. Обновить логирование

**Влияние на производительность:**
- Текущий подход: 12 инициализаций OCR модуля (все пропущены)
- Оптимальный подход: 0 инициализаций
- Экономия времени: ~20 секунд на 30 писем (~20-30% для писем с вложениями)

**Сложность:** Средняя  
**Временные рамки:** 2-3 дня  
**Приоритет:** 🔴 КРИТИЧЕСКИЙ (влияет на производительность и архитектуру)

### 3. ВЫСОКАЯ: JSON Schema валидация - некорректные типы данных

**Описание:**  
В 6 письмах LLM вернул данные с некорректными типами, которые были исправлены автокоррекцией.

**Примеры:**
- `email_002`: `None is not of type 'integer'` для `interaction.contact_id`
- `email_008`: `'info_request' is not one of ['requested_quote', 'sent_quote', ...]`
- `email_015`: `None is not of type 'string'`
- `email_017`: `None is not of type 'integer'` для `contact.organization_id`
- `email_018`: `None is not of type 'integer'` для `contact.organization_id`
- `email_019`: `'info_request' is not one of [...]` + 2x `None is not of type 'integer'`

**Причина:**  
LLM не всегда строго следует JSON Schema:
- Возвращает `null` вместо обязательных значений
- Использует недопустимые значения для enum полей
- Пропускает обязательные связи (contact_id, organization_id)

**Метод устранения:**
1. Улучшить промпт с явными примерами корректных значений
2. Добавить в промпт строгие инструкции о недопустимости null для обязательных полей
3. Реализовать pre-validation перед основной валидацией
4. Добавить примеры enum значений в промпт
5. Рассмотреть использование structured output (если поддерживается провайдером)

**Сложность:** Средняя  
**Временные рамки:** 3-5 дней  
**Приоритет:** 🟠 ВЫСОКИЙ

### 5. СРЕДНЯЯ: Отсутствие путей к вложениям

**Описание:**  
В 15+ случаях система предупреждает: "⚠️ У вложения 'unknown' отсутствует путь к файлу"

**Примеры:**
- `email_002`: 2 вложения без пути
- `email_012`: 1 вложение без пути
- `email_014`: 3 вложения без пути
- `email_016`: 3 вложения без пути
- `email_020`: 1 вложения без пути
- `email_022`: 3 вложения без пути
- И другие...

**Причина:**  
Метаданные вложений в исходных JSON файлах писем не содержат корректных путей к файлам. Возможно:
- Проблема на этапе парсинга писем
- Вложения не были сохранены
- Некорректное формирование путей

**Метод устранения:**
1. Проверить логику парсинга и сохранения вложений
2. Добавить валидацию наличия файлов вложений при парсинге
3. Логировать отсутствующие вложения на этапе парсинга, а не обработки
4. Реализовать fallback для восстановления путей по имени файла

**Сложность:** Средняя  
**Временные рамки:** 2-3 дня
