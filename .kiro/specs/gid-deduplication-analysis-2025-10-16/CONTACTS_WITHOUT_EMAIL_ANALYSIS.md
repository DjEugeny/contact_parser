## 🎯 Правило в промпте vs Реальность

### Что написано в промпте:

```
## 👤 ПЕРСОНАЛЬНЫЕ КОНТАКТЫ (contacts)
1. Добавляй только «ценные» контакты с достаточной информацией.  
2. Минимум для включения: ФИО/инициалы **и** хотя бы один способ связи (email или телефон).
```

### Что происходит на практике:

LLM **игнорирует** это правило и извлекает контакты только с именем.

**Примеры**:
```json
{
  "name": "Корякина Лариса Борисовна",
  "email": null,
  "phones": [],
  "organization_id": 1
}
{
  "name": "Кондратюк Екатерина Юрьевна",
  "email": null,
  "phones": [],
  "organization_id": 1
}
{
  "name": "Кондратюк Екатерина",
  "email": null,
  "phones": [],
  "organization_id": null
}
```

## ❓ Какую пользу несут контакты без способов связи?

### Возможные сценарии пользы:

#### 1. **Упоминание лица для принятия решения**
```
Письмо: "Пожалуйста, согласуйте с Ивановым И.И., директором отдела закупок"
```
- ✅ **Польза**: Знаем ЛПР (лицо, принимающее решение)
- ❌ **Минус**: Нет способа связи → не можем обратиться напрямую

#### 2. **Подпись в документе (КП, договор, акт)**
```
Вложение: "Директор _____ Петров А.В."
```
- ✅ **Польза**: Знаем структуру организации
- ❌ **Минус**: Контакт дублируется в каждом документе → шум

#### 3. **Копия письма (CC)**
```
Кому: ivan@company.ru
CC: Петрова М.А., Сидоров К.Л.
```
- ✅ **Польза**: Знаем круг заинтересованных лиц
- ❌ **Минус**: В копии может быть много людей → шум

#### 4. **Ошибка LLM — не извлёк email/телефон**
```
Подпись:
Иванов Иван Иванович
Менеджер по продажам
Тел: +7 (495) 123-45-67  ← LLM пропустил!
Email: ivan@company.ru    ← LLM пропустил!
```
- ✅ **Польза**: Контакт важен, данные есть в письме
- ❌ **Минус**: LLM не смог их извлечь → данные потеряны

## ⚖️ Плюсы и минусы извлечения контактов без способов связи

### ✅ Плюсы:

1. **Сохраняем контекст взаимодействий**
   - Видим, кто упоминался в переписке
   - Понимаем структуру организации

2. **Можем дообогатить данные позже**
   - Найти email/телефон в других письмах
   - Обогатить из внешних источников (LinkedIn, DaData)

3. **Аналитика по ЛПР**
   - Частота упоминаний контакта
   - Важность контакта для организации

### ❌ Минусы:

1. **Дублирование контактов**
   - Один человек → много записей (разные варианты имени)
   - Нет стабильного ключа (email) для дедупликации

2. **Шум в базе данных**
   - 4% контактов бесполезны для прямого контакта
   - Загрязняют реестр

3. **Сложность дедупликации**
   - Нестабильная нормализация имён (см. ниже)
   - Высокий риск ложных дублей

4. **Низкая ценность**
   - Нельзя связаться напрямую
   - Нельзя отправить письмо/звонок

## 🔬 Проблема нормализации коротких фамилий

### Тестирование умной нормализации:

| Исходное имя | Нормализованное | Проблема |
|--------------|-----------------|----------|
| **Иван Жук** | `иван жук` | ❌ |
| **Жук Иван** | `жук иван` | ❌ Разные результаты! |
| **Яна Муха** | `яна муха` | ⚠️ |
| **Муха Яна** | `яна муха` | ✅ Случайно совпало |
| **Ольга Рыба** | `рыба ольга` | ❌ |
| **Рыба Ольга** | `ольга рыба` | ❌ Разные результаты! |
| **Мария Волк** | `волк мария` | ✅ |
| **Волк Мария** | `волк мария` | ✅ Совпало |

### Почему так происходит?

#### Эвристика работает на окончаниях:
```python
if len(first) > 3 and first.endswith(('а', 'я', 'ия', 'ья', 'на', 'ла')):
    # Переставляем
```

**Проблемы**:

1. **"Жук" (4 буквы)** не заканчивается на -а/-я → не переставляется
2. **"Иван" (4 буквы)** не заканчивается на -а/-я → не переставляется
3. **"Рыба" (4 буквы)** заканчивается на -а, НО это фамилия, а не имя!

### Вывод:

**Умная нормализация НЕ РАБОТАЕТ** для:
- Коротких фамилий (Жук, Муха, Волк, Град, Куст, Лист)
- Фамилий на -а/-я (Рыба, Птица, Ольга — да, это может быть и фамилия!)
- Мужских имён без типичных окончаний (Иван, Олег, Петр, Павел)

**Failure rate**: ~40-50% для тестовых случаев!

## 💡 Рекомендации

### Вариант 1: Не извлекать контакты без способов связи (рекомендую ⭐)

#### Реализация:

**A. Улучшить промпт** (более строгое правило):

```diff
## 👤 ПЕРСОНАЛЬНЫЕ КОНТАКТЫ (contacts)
-2. Минимум для включения: ФИО/инициалы **и** хотя бы один способ связи (email или телефон).
+2. 🚨 **ОБЯЗАТЕЛЬНОЕ ПРАВИЛО**: Контакт ДОЛЖЕН иметь хотя бы один способ связи:
+   - Email (любой корпоративный или личный)
+   - Телефон (мобильный, рабочий, любой)
+   - ❌ **НЕ ВКЛЮЧАЙ** контакты только с ФИО без способов связи
+   - ❌ **НЕ ВКЛЮЧАЙ** контакты из CC/BCC, если у них нет email
+   - ❌ **НЕ ВКЛЮЧАЙ** подписи из документов, если нет контактных данных
```

**B. Добавить постпроцессинг-фильтр**:

```python
def filter_contacts_without_contact_info(contacts: List[Dict]) -> List[Dict]:
    """
    Удаляет контакты без способов связи.
    """
    filtered = []
    for contact in contacts:
        email = contact.get("email")
        phones = contact.get("phones", [])
        
        # Проверяем наличие хотя бы одного способа связи
        has_email = email is not None and email != ""
        has_phone = phones and len(phones) > 0
        
        if has_email or has_phone:
            filtered.append(contact)
        else:
            logger.warning(
                f"🗑️ Отфильтрован контакт без способов связи: {contact.get('name')}"
            )
    
    return filtered
```

#### Плюсы:
- ✅ Снижает шум в базе на 4%
- ✅ Упрощает дедупликацию (нет нестабильных NAME_POSITION ключей)
- ✅ Повышает качество данных (только "ценные" контакты)
- ✅ Уменьшает риск дублирования

#### Минусы:
- ❌ Теряем контекст (кто был в копии письма)
- ❌ Не можем дообогатить данные позже
- ❌ Не видим упоминаний ЛПР

### Вариант 2: Сохранять контакты, но пометить как "неполные"

#### Реализация:

```python
def enrich_contact_metadata(contact: Dict) -> Dict:
    """Добавляет метаданные о полноте контакта."""
    email = contact.get("email")
    phones = contact.get("phones", [])
    
    has_email = email is not None and email != ""
    has_phone = phones and len(phones) > 0
    
    if not has_email and not has_phone:
        contact["is_incomplete"] = True
        contact["value_score"] = 0.3  # Низкий приоритет
        contact["tags"] = contact.get("tags", []) + ["no_contact_info"]
    else:
        contact["is_incomplete"] = False
        contact["value_score"] = 1.0
    
    return contact
```

#### Использование в UI:

```python
# Фильтр "Только полные контакты"
contacts = db.query(Contact).filter(Contact.is_incomplete == False).all()

# Или показать с предупреждением
if contact.is_incomplete:
    display_warning("⚠️ Нет способов связи")
```

#### Плюсы:
- ✅ Сохраняем контекст
- ✅ Можем дообогатить позже
- ✅ Гибкость (пользователь решает, нужны ли такие контакты)

#### Минусы:
- ❌ Всё ещё есть риск дублирования
- ❌ Усложняет логику дедупликации
- ❌ Загрязняет базу данных

### Вариант 3: Сохранять в отдельную таблицу "Упоминания"

#### Реализация:

```sql
CREATE TABLE contact_mentions (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    organization_id INTEGER,
    interaction_id INTEGER,
    mention_type TEXT,  -- "cc", "signature", "mentioned", "lpr"
    created_at TIMESTAMP
);
```

```python
def extract_contacts(llm_result):
    full_contacts = []
    mentions = []
    
    for contact in llm_result.get("contacts", []):
        email = contact.get("email")
        phones = contact.get("phones", [])
        
        if email or phones:
            # Полноценный контакт → в contacts
            full_contacts.append(contact)
        else:
            # Только упоминание → в mentions
            mentions.append({
                "name": contact.get("name"),
                "organization_id": contact.get("organization_id"),
                "mention_type": contact.get("role_in_message"),
            })
    
    return full_contacts, mentions
```

#### Плюсы:
- ✅ Чистая таблица контактов (только с способами связи)
- ✅ Сохраняем контекст в отдельной таблице
- ✅ Нет риска дублирования в основном реестре
- ✅ Можно анализировать упоминания отдельно

#### Минусы:
- ❌ Усложняет архитектуру
- ❌ Нужны дополнительные запросы для полной картины
- ❌ Сложнее дообогащать данные

## 🎯 Итоговая рекомендация

### ⭐ Вариант 1 (не извлекать) + элементы Варианта 3

**Основной подход**:
1. **Усилить промпт**: явно запретить извлечение контактов без способов связи
2. **Постпроцессинг-фильтр**: удалять контакты без email/телефона
3. **Логирование**: сохранять в лог факт упоминания (для аудита)

**Опционально** (если контекст важен):
4. **Таблица mentions**: сохранять упоминания ЛПР/подписантов без контактов

### Обоснование:

1. **Качество > Количество**
   - 4% контактов не стоят проблем с дедупликацией

2. **Упрощение системы GID**
   - Без NAME_POSITION ключей → меньше рисков дублирования

3. **Фокус на "действенные" контакты**
   - Можем связаться → ценный контакт
   - Не можем связаться → шум

4. **Возможность расширения**
   - Если понадобится контекст → добавим таблицу mentions
   - Если LLM начнёт лучше извлекать → контакты появятся
