# 📊 ДЕТАЛЬНЫЙ АНАЛИЗ СЛУЧАЕВ ДУБЛИРОВАНИЯ GID

## 🔍 Случай 1: Костюшева Евгения

### Письма:
- `email_014` (2025-08-27) — GID: `62cbba63-8acd-5cb4-a311-f63f6872e03e`
- `email_016` (2025-08-27) — GID: `feb95f8e-923b-5098-b6b1-d01f60431b10`
- `email_017` (2025-08-27) — GID: `feb95f8e-923b-5098-b6b1-d01f60431b10`

### Данные контакта:

| Письмо | Имя | Email | Organization ID | Organization GID |
|--------|-----|-------|-----------------|------------------|
| email_014 | Костюшева Евгения | e.kostyusheva@helicon.ru | 2 | `3e4c9767-d143-5682-a73e-d3efce229c5c` |
| email_016 | Костюшева Евгения | e.kostyusheva@helicon.ru | 2 | `79ef90eb-b1bc-547f-9121-003d2b620b71` |
| email_017 | Костюшева Евгения | e.kostyusheva@helicon.ru | 2 | `79ef90eb-b1bc-547f-9121-003d2b620b71` |

### Ключи дедупликации:

**email_014**:
```json
{
  "match_rule": "EMAIL",
  "key_tuple": [
    "CONTACT",
    "EMAIL",
    "3e4c9767-d143-5682-a73e-d3efce229c5c",  // ← Org GID #1
    "e.kostyusheva@helicon.ru"
  ]
}
```

**email_016**:
```json
{
  "match_rule": "EMAIL",
  "key_tuple": [
    "CONTACT",
    "EMAIL",
    "79ef90eb-b1bc-547f-9121-003d2b620b71",  // ← Org GID #2 (ДРУГОЙ!)
    "e.kostyusheva@helicon.ru"
  ]
}
```

### Root Cause:

**Организация "Компания Хеликон" получила РАЗНЫЕ GID** в разных письмах:

| Письмо | Org Name | Website | Org GID | Match Rule | Key Tuple |
|--------|----------|---------|---------|------------|-----------|
| email_014 | Компания Хеликон | `null` | `3e4c9767...` | `FALLBACK` | `["ORG", "FALLBACK", "e098bb7f1e6c29d0"]` |
| email_016 | Компания Хеликон | `null` | `79ef90eb...` | `NAME_CITY` | `["ORG", "NAME_CITY", "компания хеликон", "новосибирск"]` |
| email_017 | Компания Хеликон | `helicon.ru` | `79ef90eb...` | `DOMAIN` | `["ORG", "DOMAIN", "helicon.ru"]` |

### Почему так произошло?

1. **email_014**: Организация БЕЗ website, БЕЗ города → использовался `FALLBACK` ключ (хеш случайный)
2. **email_016**: Организация БЕЗ website, НО ЕСТЬ город → использовался `NAME_CITY` ключ
3. **email_017**: Организация С website → использовался `DOMAIN` ключ

**Вывод**: В `email_014` LLM не извлёк website и город, поэтому организация получила **случайный** FALLBACK ключ. В следующих письмах данные были полнее, и организация получила **детерминированный** ключ.

## 🔍 Случай 2: Кондратюк Екатерина

### Письма:
- `email_009` (2025-08-27) — GID: `dc4f5a5b-0152-5f88-be06-8aa26ab8a250`
- `email_009` (2025-08-28) — GID: `005d3d01-4ea6-5ade-9fe8-d569bf33653f`

### Данные контакта:

| Письмо | Имя | Email | Organization ID |
|--------|-----|-------|-----------------|
| 2025-08-27 | Кондратюк Екатерина | `null` | `null` |
| 2025-08-28 | Кондратюк Екатерина | `kondratyuk_eyu@cnmt.ru` | `null` |

### Ключи дедупликации:

**2025-08-27**:
```json
{
  "match_rule": "NAME_POSITION",
  "key_tuple": [
    "CONTACT",
    "NAME_POSITION",
    "PERSONAL",
    "екатерина кондратюк",  // ← Имя в обратном порядке!
    "к.б.н., биолог"
  ]
}
```

**2025-08-28**:
```json
{
  "match_rule": "EMAIL",
  "key_tuple": [
    "CONTACT",
    "EMAIL",
    "PERSONAL",
    "kondratyuk_eyu@cnmt.ru"  // ← Email как основной ключ
  ]
}
```

### Root Cause:

**В первом письме LLM не извлёк email**, поэтому использовался `NAME_POSITION` ключ.  
**Во втором письме email был извлечён**, поэтому использовался `EMAIL` ключ.

### Дополнительная проблема:

**LLM извлекает имя в разном порядке**:
- Письмо 1: "Кондратюк Екатерина" → нормализация → `"кондратюк екатерина"`
- Письмо 2: "Екатерина Кондратюк" → нормализация → `"екатерина кондратюк"`

Функция `norm_contact_name()` **не переставляет** слова, она просто делает lowercase. Поэтому порядок слов в ключе зависит от того, как LLM извлёк имя.

**Проблема**: Даже если бы в обоих письмах использовался `NAME_POSITION` ключ, порядок слов отличается → разные ключи → разные GID.

**Вывод**: Отсутствие email в одном из писем + **вариативный порядок слов от LLM** = разные GID.

## 🔍 Случай 3: Воронова Светлана / Светлана Сергеевна

### Письма:
- `email_009` (2025-08-27) — GID: `aa275056-36e1-5d9a-b6ef-3803d33e353f`
- `email_009` (2025-08-28) — GID: `7f596bfb-83e0-5330-99f5-ce4a4876a24f`

### Данные контакта:

| Письмо | Имя | Email | Organization ID |
|--------|-----|-------|-----------------|
| 2025-08-27 | Воронова Светлана | `s.voronova@dna-technology.ru` | 1 (ДНК-Технология) |
| 2025-08-28 | Светлана Сергеевна | `s.voronova@dna-technology.ru` | `null` |

### Ключи дедупликации:

**2025-08-27**:
```json
{
  "match_rule": "EMAIL",
  "key_tuple": [
    "CONTACT",
    "EMAIL",
    "58a49494-b44e-5b2f-9263-0ce9005f10e3",  // ← Org GID (ДНК-Технология)
    "s.voronova@dna-technology.ru"
  ],
  "source": "registry"  // ← Уже был в реестре
}
```

**2025-08-28**:
```json
{
  "match_rule": "EMAIL",
  "key_tuple": [
    "CONTACT",
    "EMAIL",
    "PERSONAL",  // ← Контакт БЕЗ организации!
    "s.voronova@dna-technology.ru"
  ],
  "source": "new"  // ← Создан новый
}
```

### Root Cause:

**В первом письме** контакт связан с организацией (organization_id: 1), поэтому ключ содержит `org_gid`.  
**Во втором письме** LLM не связал контакт с организацией (organization_id: null), поэтому ключ содержит `"PERSONAL"`.

### Почему LLM не связал с организацией?

Возможные причины:
1. В письме не было явного упоминания организации "ДНК-Технология"
2. LLM решил, что это личная переписка
3. Контакт был отфильтрован постпроцессингом (низкий `value_score`)

**Вывод**: Одинаковый email, но разный `organization_id` → разные ключи → разные GID.

## 🎯 Общие паттерны

### 1. **Вариативность данных от LLM**
LLM извлекает разные данные из разных писем для одного контакта:
- То есть email, то нет
- То есть организация, то нет
- То есть website у организации, то нет

### 2. **Жёсткая привязка к organization_gid**
Ключ контакта включает `organization_gid`:
```
["CONTACT", "EMAIL", <org_gid>, <email>]
```

Если `org_gid` меняется → ключ меняется → GID меняется.

### 3. **Приоритет ключей не учитывает стабильность**
Текущий порядок приоритета:
1. EMAIL (самый стабильный) ✅
2. PHONE (средняя стабильность) ⚠️
3. NAME_POSITION (низкая стабильность) ❌

Но если email отсутствует, используется NAME_POSITION, который очень нестабильный.

## 💡 Выводы

1. **Проблема #1**: Организации получают разные GID из-за неполных данных
2. **Проблема #2**: Контакты получают разные GID при изменении organization_id
3. **Проблема #3**: Отсутствие fallback механизма для поиска существующих GID

**Главная причина**: Система GID **слишком жёсткая** и не учитывает **вариативность данных от LLM**.
