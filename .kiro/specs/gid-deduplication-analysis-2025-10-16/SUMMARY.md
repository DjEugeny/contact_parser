# 📋 ИТОГОВЫЙ ОТЧЁТ: ПРОБЛЕМЫ ДЕДУПЛИКАЦИИ GID

## 🎯 Executive Summary

**Проблема**: Одинаковые люди получают разные глобальные идентификаторы (GID) в разных письмах, что ломает основную функцию системы — дедупликацию контактов.

**Масштаб**: Обнаружено 3 случая дублирования из 5 проанализированных писем (60% failure rate).

**Корневая причина**: GID ключи слишком специфичны и зависят от вариативных данных (organization_id, наличие email, порядок слов в имени).

**Рекомендация**: Внедрить двухуровневую систему ключей с глобальными PRIMARY ключами и контекстными ALIAS ключами.

**Риски**: Критический риск деградации существующих GID. Требуется плавная миграция с версионированием.

**Сроки внедрения**: 4-6 недель с учётом тестирования и миграции.

## 🔬 Корневые причины

### 1. Жёсткая привязка к organization_gid
```python
key = ("CONTACT", "EMAIL", org_gid, email)  # ← org_gid в ключе!
```

**Проблема**: Если org_gid меняется → ключ меняется → GID меняется.

### 2. Случайный FALLBACK для организаций
```python
fallback_key = sha256(json.dumps(org)).hex()[:8]  # ← Зависит от ВСЕХ полей!
```

**Проблема**: Изменение любого поля организации → новый хеш → новый GID.

### 3. Отсутствие fuzzy matching
```python
gid = self.key_index.get(key)  # ← Только точное совпадение!
```

**Проблема**: Нет поиска похожих контактов перед созданием нового GID.

### 4. Нестабильный порядок ключей
```python
# Если email отсутствует, используется NAME_POSITION
key = ("CONTACT", "NAME_POSITION", org_key, name, position)
```

**Проблема**: Порядок слов в имени нестабилен ("Кондратюк Екатерина" vs "Екатерина Кондратюк").

## 💡 Предложенное решение

### ⭐ ПРИНЯТО: Вариант 1 + элементы Варианта 3

**Решение**:
1. **Не извлекать** контакты без способов связи (email/телефон)
2. **Сохранять упоминания** в отдельную таблицу `contact_mentions`
3. **Двухуровневая система ключей** для контактов с email/телефоном

### Двухуровневая система ключей

#### Уровень 1: PRIMARY (глобальные)
```python
# Не зависят от organization_id
("CONTACT", "EMAIL_GLOBAL", email)
("ORG", "DOMAIN", domain)
("ORG", "NAME", name)  # Вместо случайного FALLBACK
```

#### Уровень 2: ALIAS (контекстные)
```python
# Связывают контакт с организацией
("CONTACT", "EMAIL_IN_ORG", org_gid, email)
("CONTACT", "PHONE_IN_ORG", org_gid, phone)
```

### Ключевые изменения:

1. **EMAIL_GLOBAL** — первый и главный ключ, не зависит от org_gid
2. **Детерминированный fallback** для организаций (по названию, не случайный хеш)
3. **Fuzzy matching** перед созданием нового GID
4. **Версионирование** для плавной миграции

### Пример работы:

```python
# Письмо 1: Воронова Светлана с organization_id = 1
keys = [
    ("CONTACT", "EMAIL_GLOBAL", "s.voronova@dna-technology.ru"),  # PRIMARY
    ("CONTACT", "EMAIL_IN_ORG", "org-gid-1", "s.voronova@dna-technology.ru")  # ALIAS
]
gid = resolve_contact(keys)  # → GID-A

# Письмо 2: Светлана Сергеевна с organization_id = null
keys = [
    ("CONTACT", "EMAIL_GLOBAL", "s.voronova@dna-technology.ru"),  # PRIMARY (тот же!)
    # Нет EMAIL_IN_ORG (нет организации)
]
gid = resolve_contact(keys)  # → GID-A (тот же!) ✅
```

## ⚠️ Риски и митигация

### 🔴 Критический: Случайное объединение разных людей

**Риск**: Два разных человека с одинаковым email (ivan@gmail.com) получат один GID.

**Митигация**:
1. **Whitelist** личных доменов (gmail, yandex, mail) → для них сохранить org_gid в ключе
2. **Проверка контекстов**: если контакт уже связан с ДРУГОЙ организацией → проверить дополнительные сигналы
3. **Высокий порог** для fuzzy match (95%+ для личных email)

### 🔴 Критический: Деградация существующих GID

**Риск**: Изменение логики ключей → все существующие контакты получат НОВЫЕ GID.

**Митигация**:
1. **Версионирование**: поддержка v1 и v2 ключей одновременно
2. **Автоматическая миграция**: при обращении к старому ключу → добавить v2 алиас
3. **Плавное внедрение**: 4-6 недель с мониторингом

### 🟠 Высокий: Ложные fuzzy match

**Риск**: Объединение людей с похожими именами (Иванов И.И. vs Иванов И.П.).

**Митигация**:
1. **Умное сравнение имён**: учитывать части ФИО отдельно
2. **Требовать совпадение домена** для корпоративных email
3. **Ручная модерация** для низкой уверенности (85-90%)
