# ❓ FAQ: Часто задаваемые вопросы

## 1. Будет ли одинаковый GID для "Кондратюк Екатерина" и "Екатерина Кондратюк"?

### Если есть EMAIL — ✅ ДА

```python
# Любой порядок имени → один GID
("CONTACT", "EMAIL_GLOBAL", "kondratyuk_eyu@cnmt.ru") → GID-A
```

Имя вообще не учитывается в ключе, используется только email.

### Если НЕТ EMAIL — ✅ ДА (с умной нормализацией)

```python
# Оба варианта → одинаковая нормализация
norm_contact_name_smart("Кондратюк Екатерина")  # → "кондратюк екатерина"
norm_contact_name_smart("Екатерина Кондратюк")  # → "кондратюк екатерина"

# Один ключ → один GID
("CONTACT", "NAME_POSITION", "PERSONAL", "кондратюк екатерина", "") → GID-A
```

**Механизм**: Умная нормализация определяет, что стоит первым (имя/фамилия) и приводит к формату "фамилия имя".

### Дополнительная защита: алиасы

Если нормализация ошиблась, контакт всё равно найдётся по альтернативному ключу:

```python
# PRIMARY
("CONTACT", "NAME_POSITION", "PERSONAL", "кондратюк екатерина", "") → GID-A

# ALIAS (если нормализация перевернула неправильно)
("CONTACT", "NAME_POSITION_ALT", "PERSONAL", "екатерина кондратюк", "") → GID-A
```

## 2. Как определяется, что стоит первым — имя или фамилия?

### Эвристика по окончаниям

Русские **имена** обычно заканчиваются на:
- `-а`: Екатерина, Анна, Ирина
- `-я`: Мария, Юлия, Наталья
- `-ия`: Виктория, София
- `-ья`: Дарья, Софья

Русские **фамилии** обычно заканчиваются на:
- `-ов`, `-ев`: Иванов, Петров
- `-ин`: Ильин, Смирнов
- `-ский`: Достоевский
- `-ук`, `-юк`: Кондратюк
- `-ова`, `-ева` (женские): Иванова, но это редкость в первой позиции

### Алгоритм:

```python
if первое_слово.endswith(('а', 'я', 'ия', 'ья', 'на', 'ла')):
    # Скорее всего, это ИМЯ → переставляем в конец
    "Екатерина Кондратюк" → "Кондратюк Екатерина"
else:
    # Скорее всего, это ФАМИЛИЯ → оставляем как есть
    "Кондратюк Екатерина" → "Кондратюк Екатерина"
```

### Точность: ~95%

- ✅ Работает для большинства русских имён/фамилий
- ⚠️ Может ошибиться для:
  - Нетипичных фамилий: "Ольга" (может быть фамилией)
  - Иностранных имён: "John Smith"
  - Редких комбинаций: "Мария Ивановна" (оба на -а/-на)

### Защита от ошибок:

Даже если эвристика ошиблась, контакт найдётся благодаря **алиасам** — генерируются ключи для обоих вариантов порядка.

## 3. А если у контакта нет ни email, ни телефона?

Используется ключ **NAME_POSITION** с умной нормализацией:

```python
# PRIMARY: нормализованное имя
("CONTACT", "NAME_POSITION", "PERSONAL", "кондратюк екатерина", "к.б.н., биолог")

# ALIAS: исходный порядок
("CONTACT", "NAME_POSITION_ALT", "PERSONAL", "екатерина кондратюк", "к.б.н., биолог")
```

**Результат**: Контакт найдётся независимо от порядка слов.

### Дополнительно: fuzzy matching

Если не нашли точное совпадение, система ищет похожие:

```python
similar = find_similar_by_name("Екатерина Кондратюк", threshold=0.95)
# → Находит "кондратюк екатерина" с similarity=1.0 (все слова совпадают)
# → Переиспользует существующий GID
```

## 4. Что если LLM извлёк имя с ошибкой (опечатка)?

### Пример:
- Письмо 1: "Кондратюк Екатерина"
- Письмо 2: "Кондратюк Екатерина" (с опечаткой в отчестве)

### Решение: fuzzy matching

```python
# Вычисляем similarity по частям имени
parts1 = {"кондратюк", "екатерина"}
parts2 = {"кондратюк", "екатерна"}  # Опечатка

# Jaccard similarity
intersection = {"кондратюк"}  # Только 1 совпадение
union = {"кондратюк", "екатерина", "екатерна"}  # 3 слова
similarity = 1/3 = 0.33  # Низкая

# Порог = 0.95 → НЕ объединяем (создаём новый GID)
```

**Вывод**: Система **не объединит** контакты с опечатками автоматически.  
Потребуется **ручная модерация** или исправление через UI.

## 5. Как вручную объединить дубли контактов?

### Вариант 1: Добавить алиас вручную

```python
registry = GlobalIDRegistry()

# Контакт 1: GID-A ("кондратюк екатерина")
# Контакт 2: GID-B ("екатерна кондратюк" — опечатка)

# Добавляем GID-B как алиас для GID-A
registry.add_alias(
    gid="GID-A",
    alias_key=("CONTACT", "NAME_POSITION", "PERSONAL", "екатерна кондратюк", "")
)

# Теперь оба ключа ведут к GID-A
```

### Вариант 2: UI для модерации

В будущем можно добавить страницу "Потенциальные дубли":
- Система находит похожие контакты (similarity > 0.80 и < 0.95)
- Показывает пользователю пары для ручной проверки
- Пользователь подтверждает объединение → добавляется алиас

## 6. Что если контакт меняет организацию?

### Пример:
- Письмо 1: ivan@company-a.ru в организации A
- Письмо 2: ivan@company-a.ru в организации B (перешёл на новую работу)

### Решение: EMAIL_GLOBAL + проверка контекстов

```python
# Оба письма используют один PRIMARY ключ
primary = ("CONTACT", "EMAIL_GLOBAL", "ivan@company-a.ru") → GID-X

# Но разные ALIAS ключи (контексты)
alias1 = ("CONTACT", "EMAIL_IN_ORG", "org-gid-A", "ivan@company-a.ru")
alias2 = ("CONTACT", "EMAIL_IN_ORG", "org-gid-B", "ivan@company-a.ru")

# Система видит: контакт был в org-A, теперь в org-B
# → Скорее всего, тот же человек перешёл на новую работу
# → Переиспользуем GID-X, добавляем alias2
```

**Результат**: Один GID, история в обеих организациях сохранена через алиасы.

## 7. А если это РАЗНЫЕ люди с одинаковым email?

### Пример:
- Иван Петров (ivan@gmail.com) в компании A
- Другой Иван Петров (ivan@gmail.com) в компании B

### Защита: whitelist личных доменов

```python
PERSONAL_DOMAINS = {"gmail.com", "yandex.ru", "mail.ru", "yahoo.com"}

if is_personal_email("ivan@gmail.com"):
    # Для личных email СОХРАНЯЕМ org_gid в ключе (старая логика)
    key = ("CONTACT", "EMAIL", org_gid, "ivan@gmail.com")
else:
    # Для корпоративных email используем глобальный ключ
    key = ("CONTACT", "EMAIL_GLOBAL", "ivan@dna-technology.ru")
```

**Результат**:
- `ivan@gmail.com` в org-A → GID-1
- `ivan@gmail.com` в org-B → GID-2 (разные GID!) ✅
- `ivan@company-a.ru` в org-A → GID-3
- `ivan@company-a.ru` в org-B → GID-3 (один GID, т.к. корпоративный email)

## 10. Как умная нормализация обработает короткие фамилии (Жук, Муха)?

### ❌ Проблема обнаружена!

Умная нормализация **НЕ РАБОТАЕТ** для коротких фамилий и мужских имён.

### Тестовые результаты:

| Исходное имя | Нормализация | Результат |
|--------------|--------------|-----------|
| Иван Жук | `иван жук` | ❌ |
| Жук Иван | `жук иван` | ❌ **Разные!** |
| Яна Муха | `яна муха` | ⚠️ |
| Муха Яна | `яна муха` | ✅ Случайно совпало |
| Ольга Рыба | `рыба ольга` | ❌ |
| Рыба Ольга | `ольга рыба` | ❌ **Разные!** |

### Почему?

Эвристика проверяет окончание **первого слова**:

```python
if len(first) > 3 and first.endswith(('а', 'я', 'ия', 'ья', 'на', 'ла')):
    # Переставляем (считаем, что первое слово — это ИМЯ)
```

**Проблемы**:
1. **"Жук"** не заканчивается на -а/-я → не переставляется
2. **"Иван"** не заканчивается на -а/-я → не переставляется
3. **"Рыба"** заканчивается на -а, НО это фамилия! → переставляется неправильно

### Failure rate: ~40-50% для коротких фамилий

### Решение?

**Вариант А: Улучшить эвристику** (сложно, не гарантирует 100%)

```python
# Добавить словарь популярных фамилий
COMMON_SURNAMES = {"жук", "муха", "волк", "град", "рыба", ...}

if first in COMMON_SURNAMES:
    # Не переставляем (это фамилия)
    pass
```

**Минус**: Словарь не покроет все случаи.

**Вариант Б: Генерировать ОБА варианта как алиасы** (надёжнее ✅)

```python
# PRIMARY: как есть (без перестановки)
yield ("CONTACT", "NAME_POSITION", org_key, "иван жук", position)

# ALIAS: перевёрнутый вариант
yield ("CONTACT", "NAME_POSITION_ALT", org_key, "жук иван", position)
```

**Результат**: Контакт найдётся по **любому** варианту порядка.

**Вариант В: Не полагаться на NAME для дедупликации** (лучший ✅)

Если у контакта нет email/телефона → **не извлекать** его вообще (см. вопрос 11).

## 11. Стоит ли извлекать контакты БЕЗ email и телефона?

### 📊 Текущая ситуация:

- **4.2%** контактов не имеют ни email, ни телефона (8 из 191)
- LLM **игнорирует** правило промпта о минимуме данных

### ❌ Проблемы таких контактов:

1. **Высокий риск дублирования**
   - Нет стабильного ключа (email)
   - Нормализация имён нестабильна (особенно для коротких фамилий)
   - Один человек → много записей

2. **Низкая ценность**
   - Нельзя связаться напрямую
   - Нельзя отправить письмо/звонок
   - Только информационная ценность

3. **Шум в базе данных**
   - 4% бесполезных для контакта записей
   - Усложняют поиск и аналитику

### ✅ Возможная польза:

1. **Контекст взаимодействий**
   - Видим, кто упоминался в переписке
   - ЛПР (лицо, принимающее решение)

2. **Структура организации**
   - Должности, подразделения

3. **Дообогащение позже**
   - Найти данные в других письмах
   - Обогатить из внешних источников

### 💡 Рекомендация: **НЕ извлекать** ⭐

#### Обоснование:

1. **Качество > Количество**
   - 4% контактов не стоят проблем с дедупликацией
   - Фокус на "действенные" контакты (с которыми можно связаться)

2. **Упрощение GID системы**
   - Без NAME_POSITION ключей → меньше рисков
   - EMAIL/PHONE — стабильные ключи

3. **Чистота данных**
   - Только контакты с реальной ценностью
   - Меньше шума в поиске и аналитике

#### Реализация:

**A. Усилить промпт**:

```
🚨 **ОБЯЗАТЕЛЬНОЕ ПРАВИЛО**: 
Контакт ДОЛЖЕН иметь хотя бы один способ связи:
- Email (любой)
- Телефон (любой)

❌ НЕ ВКЛЮЧАЙ:
- Контакты только с ФИО без способов связи
- Подписи из документов без email/телефона
- CC/BCC без email
```

**B. Постпроцессинг-фильтр**:

```python
def filter_contacts_without_contact_info(contacts):
    """Удаляет контакты без способов связи."""
    return [
        c for c in contacts 
        if c.get("email") or (c.get("phones") and len(c["phones"]) > 0)
    ]
```

#### Альтернатива: Сохранять в отдельную таблицу

Если контекст важен:

```sql
CREATE TABLE contact_mentions (
    name TEXT,
    organization_id INTEGER,
    mention_type TEXT,  -- "cc", "lpr", "mentioned"
    interaction_id INTEGER

```

**Результат**: 
- Основная таблица `contacts` чистая (только с email/телефоном)
- Упоминания хранятся отдельно для аналитики

### Ожидаемый эффект:

| Метрика | До | После |
|---------|-----|-------|
| Контактов без связи | 4.2% | 0% |
| Риск дублирования | Высокий | Низкий |
