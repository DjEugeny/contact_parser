# Requirements Document: Phones UI Format from Normalized

## Введение

Данная спецификация направлена на устранение рассинхронизации между полями `number` и `normalized` в структуре телефонов, обеспечение единообразного UI-формата и очистку данных от лишних полей.

## Контекст и проблема

### Текущее состояние

После выполнения PLAN-004 (Phone Disambiguation) и PLAN-005 (Phone Extension Normalization) система имеет:
- ✅ Корректную структуру phone объектов с полями `{type, number, normalized, original, extension}`
- ✅ Разделение телефонов между организациями по эвристикам
- ✅ Извлечение добавочных номеров в отдельное поле `extension`
- ✅ Нормализацию в E.164 формат

### Выявленные проблемы

1. **Рассинхронизация `number` и `normalized`**: Поле `number` может содержать произвольный формат, не согласованный с `normalized`
2. **Лишние поля в phone объектах**: Например, `confidence` внутри телефона (должен быть только на уровне контакта)
3. **Отсутствие единого UI-формата**: Разные источники данных (LLM, OCR, ручной ввод) дают разные форматы отображения
4. **Неопределенность в UI-рендеринге**: Фронтенд не знает, какому полю доверять для отображения

## Requirements

### Requirement 1: Контракт данных для phone объектов

**User Story:** Как разработчик системы, я хочу иметь четкий контракт данных для phone объектов, чтобы гарантировать консистентность данных на всех этапах обработки.

#### Acceptance Criteria

1. WHEN система обрабатывает phone объект THEN он ДОЛЖЕН содержать ТОЛЬКО следующие ключи: `type`, `number`, `normalized`, `original`, `extension`
2. WHEN phone объект содержит поле `normalized` THEN оно ДОЛЖНО быть в формате E.164 (например, `+74956401771`) ИЛИ `null`
3. WHEN phone объект содержит поле `number` THEN оно ДОЛЖНО быть сгенерировано из `normalized` в UI-формате И НЕ ДОЛЖНО содержать добавочный номер
4. WHEN phone объект содержит поле `original` THEN оно ДОЛЖНО сохранять исходную строку без изменений
5. WHEN phone объект содержит поле `extension` THEN оно ДОЛЖНО содержать ТОЛЬКО цифры/DTMF символы (`0-9#*`) ИЛИ `null`
6. WHEN phone объект содержит поле `type` THEN оно ДОЛЖНО быть одним из: `mobile`, `office`, `fax`, `main`, `other`, `null`

### Requirement 2: Санитизация phone объектов

**User Story:** Как администратор данных, я хочу автоматически удалять лишние поля из phone объектов, чтобы предотвратить утечку метаданных и обеспечить чистоту данных.

#### Acceptance Criteria

1. WHEN постпроцессор обрабатывает `contacts[].phones[]` THEN он ДОЛЖЕН удалить все ключи, кроме whitelist (`type`, `number`, `normalized`, `original`, `extension`)
2. WHEN постпроцессор обрабатывает `organizations[].phones[]` THEN он ДОЛЖЕН удалить все ключи, кроме whitelist
3. WHEN санитайзер удаляет поля THEN он ДОЛЖЕН логировать это в `postprocessing_metadata.sanitizer.removed_props` с указанием GID сущности и списка удаленных ключей
4. WHEN санитайзер обнаруживает поле `confidence` внутри phone объекта THEN он ДОЛЖЕН удалить его И залогировать предупреждение
5. WHEN санитайзер завершает работу THEN итоговая JSON схема НЕ ДОЛЖНА содержать лишних полей в phone объектах

### Requirement 3: Генерация UI-формата из normalized

**User Story:** Как пользователь UI, я хочу видеть телефоны в едином, читаемом формате, чтобы легко их воспринимать и использовать.

#### Acceptance Criteria

1. WHEN постпроцессор обрабатывает phone объект с валидным `normalized` (E.164) THEN он ДОЛЖЕН перегенерировать поле `number` в UI-формат
2. WHEN номер принадлежит региону RU THEN `number` ДОЛЖЕН быть в формате `+7 (XXX) XXX-XX-XX`
3. WHEN номер принадлежит другому региону THEN `number` ДОЛЖЕН быть в формате INTERNATIONAL (libphonenumber)
4. WHEN `normalized` равен `null` ИЛИ невалиден THEN `number` ДОЛЖЕН быть fallback из `original` с базовым форматированием
5. WHEN генерация UI-формата завершена THEN поле `number` НЕ ДОЛЖНО содержать добавочный номер (extension остается в отдельном поле)
6. WHEN генерация UI-формата не удалась (exception) THEN система ДОЛЖНА использовать fallback И залогировать ошибку

### Requirement 4: Интеграция в постпроцессор

**User Story:** Как разработчик пайплайна, я хочу, чтобы генерация UI-формата и санитизация выполнялись автоматически на правильном этапе обработки.

#### Acceptance Criteria

1. WHEN постпроцессор выполняет обработку THEN санитизация phone объектов ДОЛЖНА происходить ПОСЛЕ присвоения GID И ПЕРЕД финальной нормализацией
2. WHEN постпроцессор выполняет обработку THEN генерация UI-формата ДОЛЖНА происходить ПОСЛЕ санитизации И ПЕРЕД записи файла
3. WHEN обработка завершена THEN `postprocessing_metadata` ДОЛЖЕН содержать статистику: количество обработанных телефонов, количество перегенерированных `number`, количество удаленных полей
4. WHEN происходит ошибка в обработке phone объекта THEN система ДОЛЖНА продолжить обработку остальных И залогировать ошибку
5. WHEN обработка завершена THEN все phone объекты в `contacts[]` и `organizations[]` ДОЛЖНЫ соответствовать контракту данных

### Requirement 5: UI-рендеринг (фронтенд guidelines)

**User Story:** Как фронтенд-разработчик, я хочу иметь четкие правила отображения телефонов, чтобы обеспечить консистентный UX.

#### Acceptance Criteria

1. WHEN UI отображает телефон THEN он ДОЛЖЕН использовать поле `number` (уже в UI-формате)
2. WHEN phone объект содержит `extension` THEN UI ДОЛЖЕН добавить `" (доб. {extension})"` к отображению
3. WHEN UI создает click-to-call ссылку THEN он ДОЛЖЕН использовать `tel:{normalized}` И, при наличии extension, добавить `;ext={extension}` ИЛИ `,{extension}` как fallback
4. WHEN UI отображает телефон для аудита/диагностики THEN он МОЖЕТ показать поле `original` в отдельном контексте
5. WHEN `normalized` равен `null` THEN UI ДОЛЖЕН показать `number` без click-to-call функциональности

### Requirement 6: Обратная совместимость и миграция

**User Story:** Как администратор системы, я хочу, чтобы существующие данные корректно обрабатывались после внедрения изменений.

#### Acceptance Criteria

1. WHEN система обрабатывает старые данные с рассинхронизированными `number`/`normalized` THEN она ДОЛЖНА перегенерировать `number` из `normalized`
2. WHEN система обрабатывает phone объекты с лишними полями THEN она ДОЛЖНА их удалить И залогировать
3. WHEN система обрабатывает данные без поля `normalized` THEN она ДОЛЖНА использовать fallback форматирование для `number`
4. WHEN миграция завершена THEN все существующие файлы ДОЛЖНЫ соответствовать новому контракту данных
5. WHEN происходит ошибка миграции THEN система ДОЛЖНА залогировать детали И продолжить обработку

## Критерии успеха

1. **Консистентность данных**: 100% phone объектов соответствуют контракту данных (только whitelist полей)
2. **UI-формат**: 100% phone объектов с валидным `normalized` имеют корректно сгенерированный `number`
3. **Санитизация**: Все лишние поля удалены, логи содержат детали удаления
4. **Метаданные**: `postprocessing_metadata` содержит полную статистику обработки
5. **Регрессия**: Нет ошибок валидации JSON Schema, все существующие тесты проходят
6. **Производительность**: Обработка не замедляется более чем на 5%

## Зависимости

### Upstream (требуют завершения)
- ✅ PLAN-004: Phone Disambiguation (разделение телефонов между организациями)
- ✅ PLAN-005: Phone Extension Normalization (структура phone объектов)

### Downstream (будут использовать)
- Frontend UI (отображение телефонов)
- API endpoints (возврат данных клиентам)
- Database persistence (схема БД)
- Export modules (Google Sheets, CSV)

## Ограничения и допущения

### Ограничения
1. Используется библиотека `phonenumbers` (libphonenumber) для форматирования
2. Поддержка только E.164 формата для `normalized`
3. UI-формат для RU фиксирован: `+7 (XXX) XXX-XX-XX`
4. Extension поддерживает только DTMF символы: `0-9#*`

### Допущения
1. LLM может возвращать phone объекты с лишними полями (требуется санитизация)
2. Поле `normalized` может быть `null` (требуется fallback)
3. Фронтенд будет следовать guidelines по отображению
4. Существующие данные могут иметь рассинхронизацию `number`/`normalized`

## Риски

1. **Производительность**: Перегенерация `number` для всех телефонов может замедлить обработку
   - *Митигация*: Кэширование форматированных номеров, batch обработка
   
2. **Обратная совместимость**: Изменение формата `number` может сломать существующие интеграции
   - *Митигация*: Graceful degradation, логирование изменений, постепенный rollout
   
3. **Качество данных**: `normalized` может содержать ошибки, что приведет к неправильному UI-формату
   - *Митигация*: Валидация E.164 перед форматированием, fallback на `original`
   
4. **Региональные особенности**: Форматы телефонов могут отличаться в разных странах
   - *Митигация*: Использование libphonenumber для всех регионов, кроме RU (где фиксированный формат)
