
# PLAN-006: Org/End-User INN Enrichment (через ФНС + кандидаты от агрегаторов)

**Цель:** безопасно обогащать ИНН **для всех организаций**, встречающихся в письмах (поставщик, посредник, конечный пользователь, площадка и т.п.), с приоритетом официального источника **ФНС (ЕГРЮЛ/ЕГРИП)** и прозрачным следом принятия решений.

**Контекст:** текущая схема и пайплайн уже формируют объекты `organizations[]`, `contacts[]`, `interactions[]`, присваивают `gid` и ведут `postprocessing_metadata` (см. пример результата; структура полей и `gid.assigned` совпадает).
---

## 0) Основные принципы

- **Источник истины — ФНС (ЕГРЮЛ/ЕГРИП).** Поиск сведений доступен на egrul.nalog.ru; выдача — PDF-выписка/сводные данные. Для системной интеграции есть сервис «Интеграция и доступ к базам ЕГРЮЛ и ЕГРИП». citeturn0search0turn0search15turn0search7
- **Агрегатор** (DaData) используется как *ускоритель кандидатов* и для обогащения метаданными, но окончательное подтверждение ИНН — по ФНС при сомнениях. citeturn0search2turn0search1
- **Двухпороговая логика принятия:** 
  - `score ≥ 0.85` и **единственный** кандидат → auto-accept;
  - `0.65–0.85` или несколько кандидатов → needs-review (ручное подтверждение);
  - `< 0.65` → reject (не пишем ИНН).
- **Никаких новых полей на уровне `organizations[]`,** которые ломают схему (например, `confidence`). Все служебные детали — в `postprocessing_metadata.enrichment.org_inn`.
- **Один INN на GID:** ИНН хранится в карточке организации (по `gid`) и переиспользуется везде, где организация фигурирует.

## 1) Где встраивать в пайплайн

**Позиция:** после дедупа организаций и присвоения `gid` .kiro\specs\global-ID-registry\PLAN‑003, до финального сохранения результата.

Рекомендованный порядок стадий:  
`sanitize → org dedup → фильтр ценных контактов → assign gid → org_inn_enrichment → backfill/enrich → нормализация → кросс‑ссылки → телеметрия`.

Если у организации уже есть валидный ИНН (контрольная сумма/длина 10/12) — шаг обогащения **пропускается**.

## 2) Конфигурация модуля

В `config.yaml` (или конфиге процессора) добавить раздел:
```yaml

  enabled: true
  auto_accept_threshold: 0.85
  review_threshold: 0.65
  providers:
    - type: "fns_integration"     # при наличии доступа
      enabled: true
      timeout_ms: 6000
    - type: "fns_public"          # egrul.nalog.ru (парсинг выдачи/мета, если допустимо)
      enabled: true
      timeout_ms: 6000

      enabled: true

    - type: "rusprofile"
      enabled: true

    path: "registry/inn_cache.jsonl"

    allow_ip_inn: true            # политика по ИП (ИНН физлица)
    store_personal_data: "minimal"
```
> Замечание: интеграция по ФНС через официальный сервис «Интеграция…» предпочтительнее; публичный поиск egrul.nalog.ru — запасной/полуручной путь (выписки в PDF). citeturn0search7turn0search0

## 3) Нормализация и ключи для поиска кандидатов

Нормализуем признаки организации (как и для GID):
- `name_norm`: снятие юр‑форм (ООО/АО/ПАО/ИП/ФБУЗ/ФГБУ/ГБУЗ и т.п.), кавычек, пунктуации; один пробел; lower.
- `city_norm`: трим, словарь синонимов/опечаток.
- `address_norm`: улица/дом без корп./офиса, где возможно.
- `domain`: e2LD (нижний регистр, punycode).
- `email_domain`: если доступен.

Формируем «ключ запроса»: `(name_norm, city_norm, address_norm?, domain?)`.

Для валидации ИНН используем контрольную сумму и длину (10/12).

## 5) Алгоритм (per-organization)

Для каждой организации в итоговом JSON (после `gid`):
1) **Skip‑rule:** если `org.inn` уже валиден — пропустить.
2) **Overrides:** проверить `inn_overrides.yml` по `org_gid`/`name_norm+city_norm`. Если найдено → принять (`decision=override`, `confidence=1.0`, `source=local`).
3) **Cache:** поиск в `inn_cache.jsonl` (ключ `(name_norm, city_norm, domain?)`). Если не просрочено по TTL → принять.
4) **Providers (параллельно, с таймаутами):** 
   - запрос в DaData → получить **кандидатов** (name, inn, ogrn, address, opf, region);
   - при наличии доступа — запросить ФНС‑интеграцию по тем же признакам (или по ИНН от кандидата для валидации).
5) **Нормализация кандидатов:** привести названия/адреса, удалить дубликаты (по ИНН).
6) **Скоинг кандидатов:** 
   - сходство `name_norm` (симилярити);
   - совпадение `city_norm`/региона;
   - совпадение адреса (улица+дом);
   - совпадение домена сайта/email (если есть);
   - совпадение юр‑формы.
7) **Правила принятия:**
   - если `max_score ≥ auto_accept_threshold` **и** ровно один кандидат с валидным ИНН → **auto-accept** → записать `org.inn`;
   - если `review_threshold ≤ max_score < auto_accept_threshold` **или** кандидатов несколько → **needs_review** (не записывать `org.inн`);
   - иначе → **reject**.
8) **Подтверждение ФНС:** 
   - если ИНН пришёл от агрегатора → при сомнениях проверяем карточку ФНС/выписку (API/публичный сервис). 
9) **Запись следа (provenance):** подробности — в `postprocessing_metadata.enrichment.org_inn`.
10) **Кэширование:** успешные авто‑принятия + ручные подтверждения добавлять в `inn_cache.jsonl`; ручные — также в `inn_overrides.yml`.

> Важное: никакой `confidence` на уровне `organizations[]`; только `inn` и метаданные в `postprocessing_metadata` (во избежание нарушений `additionalProperties:false`).

## 10) Тест‑план

### Юнит‑тесты
- Нормализация `name_norm/city_norm/address_norm/domain`.
- Контрольная сумма ИНН (10/12).
- Скоинг кандидатов (таблица весов + пороги).
- Парсинг/адаптеры провайдеров (заглушки/фикстуры).

### Интеграционные
- На входе организация без ИНН → при единственном высоком кандидате ИНН записывается (auto-accept).
- Несколько кандидатов/средний скор → статус `needs_review`, ИНН не записан.
- Плохой сигнал → `reject`.
- Повторный прогон тех же данных берёт ИНН из кеша/override без обращений к внешним источникам.
- Обогащение не добавляет запрещённых полей в `organizations[]` (валидация зелёная).

### Регресс
- Пример из текущих результатов (структура `organizations/contacts/gid.assigned`) проходит без ошибок после внедрения обогащения. fileciteturn7file0

## 11) Acceptance Criteria (DoD)

- В итоговом JSON ИНН отсутствующие ранее появляются только при `auto-accept` (с `provenance`), при других решениях — не записываются.
- Нулевые ошибки валидации (нет лишних полей в `organizations[]`).
- `postprocessing_metadata.enrichment.org_inn` содержит полную историю решений, источники и кандидатов.
- Кеш и оверрайды создаются и используются; повторные прогоны работают детерминированно.
- Производительность/таймауты не ломают пайплайн (внешние ошибки — мягкие, с логом и деградацией до partial/no‑enrichment).

8) **Интеграция в пайплайн** (после `gid`; без изменения `organizations[]`, кроме `inn`).

## 13) Примечания по эксплуатации

- Рейтлимиты и бэкофф на внешние API; кэшировать отрицательные результаты на короткий срок (например, 1 час).
- Предпочитать кросс‑проверку: если кандидат найден агрегатором → по возможности верифицировать по ФНС.
- Для частых «одноимёнок» — ввести список «опасных названий» (требуют всегда `needs_review`).
