# Анализ и исправление критического бага с сопоставлением вложений

## 🚨 Описание проблемы

В модуле `src/advanced_email_fetcher.py` обнаружен критический баг, приводящий к неправильному сопоставлению вложений с письмами. **Проблема**: вложения из одного письма в треде показываются в других письмах того же треда, где их фактически нет.

### Примеры проявления бага

1. **Письмо `email_003_20250723_20250723_dna-technology_ru_be4fb59a.json`**:
   - Показывает 2 вложения: `АНКЕТА Участника.docx` и `Письмо для пользователей 1.1.doc`
   - **Фактически**: в этом письме нет вложений

2. **Письмо `email_006_20250723_20250723_dna-technology_ru_be4fb59a.json`**:
   - Показывает те же 2 вложения
   - **Фактически**: только это письмо содержит эти вложения

3. **Письма с thread_id `20250723_dna-technology_ru_1c456124`**:
   - Все письма (004, 009, 012, 014) показывают 3 вложения с КП
   - **Фактически**: только письмо 004 и 014 содержат вложения

## 🔍 Корневая причина анализа

### Основная проблема
Система использует `thread_id` для определения принадлежности вложений, а не уникальный `message_id`. Это приводит к тому, что все вложения треда приписываются каждому письму в треде.

### Код проблемы
В методе `check_email_processing_status()` (строки 2600-2615):

```python
if thread_id:
    # Ищем файлы с префиксом thread_id
    attachment_files = list(
        attachments_path.glob(f"*{thread_id}*")
    )
```

### Последствия
- Нарушение бизнес-логики анализа писем
- Неправильные interaction summaries
- Ошибки в анализе коммерческих предложений
- Некорректная работа модулей, зависящих от вложений
