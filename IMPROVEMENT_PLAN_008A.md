# 🎯 План улучшения TASK-008A: Устранение "мусорных" данных

## Проблема

✅ **Функция работает** - МИЛЛАБ получил город Москва  
❌ **Но есть мусор** - МИЛЛАБ и ФБУЗ получили адрес "117587" (индекс ДНК-Технология)

### Причина:
Регексы не понимают контекст. Они находят адрес в шапке документа (ДНК-Технология) и присваивают его всем организациям, упомянутым в документе.

## Решение 1: Улучшение промпта LLM (рекомендуется)

### Идея:
Добавить в системный промпт инструкцию анализировать вложения для извлечения локации организаций.

### Изменения в промпте:

```markdown
## Извлечение локации из вложений

При анализе письма с вложениями (коммерческие предложения, реквизиты, счета):

1. **Определите организации-участники:**
   - Отправитель документа (обычно в шапке)
   - Получатель документа (обычно после шапки)
   - Конечный пользователь (если указан)

2. **Извлекайте локацию ТОЛЬКО для соответствующей организации:**
   - Адрес в шапке документа → организация-отправитель
   - Адрес в блоке "Кому:" → организация-получатель
   - Адрес в блоке "Конечный пользователь:" → конечный пользователь

3. **НЕ присваивайте:**
   - Адрес отправителя → получателю
   - Адрес из шапки → всем организациям в документе

### Пример:
```
Шапка: ООО "ДНК-Технология", Адрес: 117587, г. Москва...
Кому: Компания МИЛЛАБ, Акутину Ивану

Правильно:
- ДНК-Технология: city=Москва, address=117587, г. Москва...
- МИЛЛАБ: city=null, address=null (адрес не указан для МИЛЛАБ)

Неправильно:
- МИЛЛАБ: address=117587 (это адрес ДНК-Технология!)
```
```

### Преимущества:
- ✅ LLM понимает контекст
- ✅ Не присвоит чужой адрес
- ✅ Работает с первого раза
- ✅ Не нужна сложная постобработка

### Недостатки:
- ⚠️ Зависит от качества LLM
- ⚠️ Увеличивает размер промпта (~200 токенов)

### Конфликт с постобработкой:
Если LLM уже заполнил данные, постобработка не должна их перезаписывать:

```python
# В OrgLocationEnrichment._apply_enrichment:
if self.config.apply_if_empty_only:
    if org_data.get('city') and org_data.get('address'):
        # LLM уже заполнил оба поля - не трогаем
        return {'organization': org_data, 'metadata': ...}
```

## Решение 2: Улучшение регексов (дополнительная защита)

### Проблемы в текущей реализации:

1. **Слишком широкий радиус поиска** (±500 символов)
2. **Нет проверки принадлежности адреса**
3. **Извлекается только индекс вместо полного адреса**

### Улучшения:

#### 2.1. Уменьшить радиус поиска
```python
# БЫЛО:
start_pos = max(0, org_position - 500)
end_pos = min(len(text), org_position + 500)

# СТАЛО:
start_pos = max(0, org_position - 200)  # Ближе к организации
end_pos = min(len(text), org_position + 300)  # Больше вперед, меньше назад
```

#### 2.2. Проверять принадлежность адреса
```python
def _is_address_belongs_to_org(self, address_context: str, org_name: str) -> bool:
    """Проверяет, принадлежит ли адрес организации"""
    
    # Ищем маркеры принадлежности
    ownership_markers = [
        f"{org_name}.*адрес",
        f"адрес.*{org_name}",
        "юридический адрес:",
        "фактический адрес:",
    ]
    
    # Ищем маркеры чужого адреса
    foreign_markers = [
        "отправитель:",
        "от кого:",
        "поставщик:",
    ]
    
    # Если адрес явно принадлежит другой организации - отклоняем
    for marker in foreign_markers:
        if marker in address_context.lower():
            return False
    
    return True
```

#### 2.3. Извлекать полный адрес, а не только индекс
```python
# Улучшить паттерн адреса:
self._address_patterns = [
    # Полный адрес с индексом
    re.compile(r'\b(\d{6},?\s+г\.?\s+[А-ЯЁ][^,\n]{5,100})', re.UNICODE),
    # Адрес с меткой
    re.compile(r'(?:юридический\s+)?адрес[:\s]+(\d{6}[^\.]+\.)', re.IGNORECASE | re.UNICODE),
]
```

#### 2.4. Не применять обогащение, если уверенность низкая
```python
# В OrgLocationEnrichment._apply_enrichment:
if evidence.confidence < 0.7:
    # Низкая уверенность - не применяем
    return {'organization': org_data, 'metadata': ...}
```
