## 📋 Мини-ТЗ по тестированию провайдеров LLM

📄 Техническое задание

Проект: тестирование LLM-моделей для анализа бизнес-переписки
Цель: определить оптимальную модель и провайдера (OpenRouter / Replicate) для обработки писем и вложений (контакты, саммари, коммерческие предложения) на русском языке.

1. Задачи проекта

Организовать тестирование моделей:

Этап 1: DeepSeek V3.1 (deepseek-chat-v3.1)

Этап 2: Qwen-2.5-72B-Instruct

Использовать два провайдера:

OpenRouter (с бесплатными лимитами и возможностью оплаты).

Replicate (платная среда).

Проверить работу моделей на подготовленном датасете писем и вложений.

2. Датасет

Объём 1: 10 писем + вложения (тестовый набор).

Объём 2: 30 писем + вложения (расширенный набор для проверки устойчивости).

Письма в формате JSON (тело письма + метаданные).

Вложения в формате TXT.

Для каждого письма считать количество символов и токенов (учёт нагрузки).

3. Задачи для моделей

На каждый входной пример (письмо + вложения) модель должна:

Извлечь все контакты (ФИО, email, телефоны, должность, компания).

Сформировать краткое саммари переписки (суть диалога).

Определить наличие коммерческого предложения (если есть — извлечь ключевые данные: сумма, сроки, условия).

Вернуть результат в структурированном JSON.

4. Формат ответа модели

Результаты должны быть в JSON:

{
  "contacts": [
    {
      "name": "Иван Иванов",
      "email": "ivanov@example.com",
      "phone": "+7-999-123-45-67",
      "company": "ООО Ромашка",
      "position": "менеджер по продажам"
    }
  ],
  "summary": "Краткое описание сути переписки...",
  "commercial_offer": {
    "detected": true,
    "price": "250000 руб.",
    "deadline": "30 дней",
    "conditions": "оплата по факту"
  }
}

5. Критерии оценки

Точность извлечения контактов.

Полнота и корректность саммари.

Качество обработки коммерческих предложений.

Структурированность ответа (валидный JSON).

Стабильность модели (нет отказов, одинаковые результаты на повторных запросах).

6. Сравнение

Сравнить DeepSeek V3.1 и Qwen-2.5-72B по:

точности,

скорости,

стоимости (если задействован Replicate или платные запросы OpenRouter),

устойчивости к разным типам писем (шум, длинные вложения).

Сравнить результаты OpenRouter vs Replicate (одна и та же модель).

7. Интеграционные требования

Организовать возможность переключения моделей и провайдеров в одном коде (например, через абстрактный класс LLMProvider).

Логировать:

модель и провайдер,

затраченные токены,

время ответа,

валидность JSON.

Хранить результаты тестов для последующего анализа (например, в SQLite/CSV).

8. Этапы работ

Подключение API OpenRouter и Replicate.

Тестирование DeepSeek V3.1 на датасете (10 → 30 писем).

Тестирование Qwen-2.5-72B на том же датасете.

Сравнительный анализ моделей и провайдеров.

Подготовка отчёта с выводами и рекомендациями.

⚡ В результате должно быть понятно:

какая модель лучше подходит для анализа бизнес-переписки,

какой провайдер стабильнее и выгоднее,

можно ли масштабировать решение на весь массив почты.

9. Метрики оценки

Для объективного сравнения моделей необходимо использовать набор количественных метрик.

F1-score: гармоническое среднее Precision и Recall.

👉 Требуется заранее подготовить эталонный список контактов для датасета.

9.2 Краткое саммари переписки

ROUGE-L: метрика схожести между эталонным саммари и сгенерированным (учёт длиннейшей общей подпоследовательности).

BLEU: для проверки совпадений по ключевым словам и фразам.

Человеческая оценка (1–5): эксперты оценивают качество саммари по критериям:

полнота,

точность,

стилистическая адекватность.

9.3 Коммерческие предложения

Accuracy (корректность детекции): верно ли определено наличие/отсутствие оффера.

Entity extraction correctness: совпадение выделенных ключевых данных (сумма, сроки, условия) с эталонными.

Можно считать как Precision/Recall для каждой сущности.

9.4 JSON-структура

Валидность JSON (бинарная метрика): 1 = валиден, 0 = невалиден.

Consistency (стабильность): повторные запросы на одно и то же письмо дают одинаковую структуру.

9.5 Производительность

Время отклика модели (ms).

Стоимость (токены × цена).

Частота ошибок API (timeout, отказ).

10. Сравнительный отчёт

По итогам тестирования каждая модель и провайдер должны быть оценены по:

Контактам (Precision, Recall, F1).

Саммари (ROUGE, BLEU, human score).

Офферам (accuracy + полнота извлечённых сущностей).

JSON (валидность, стабильность).

Производительности (время ответа, стоимость).

⚡ В результате получится таблица сравнения (модели × провайдеры) с числовыми метриками и финальными рекомендациями.
