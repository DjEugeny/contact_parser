### **2. Изменения для промпта LLM (на русском, вложить это в инструкцию):**

```
1. Верни результат в формате JSON как два массива: "organizations" и "contacts".

2. В "organizations" добавляй каждую уникальную компанию:
   - Собирай все найденные корпоративные email, телефоны, ИНН, сайты, город и физический/юридический адрес (address) — даже если нет привязки к конкретному человеку.
   - organization_id делай уникальным для каждой организации.
   - Если контактные данные или адрес указаны без привязки к ФИО — относить их в organizations (например, "mail@org.ru", общий телефон, адрес).

3. В "contacts" добавляй только **ценные** (валидные) контакты:
   - Минимум: ФИО или (организация + должность/роль), плюс хотя бы один способ связи (email или телефон).
   - Каждый персональный контакт должен содержать organization_id, city (если есть, либо дублировать из организации).
   - Добавляй поле address для человека, если оно встречается отдельно (например, филиал, домашний адрес).

4. Не извлекать/не включать в contacts:
   - Записи без ФИО, должности/роли или организации, и без способов связи.
   - Только корпоративные/организационные email и телефоны — относить их к organizations.

5. В каждом контакте и каждой организации обязательно заполняй поле "address" и "city", если есть в явном виде; иначе для контакта подставлять значение из organization.
```

## **3. Постобработка: полный алгоритм**

### **a) Дедупликация и объединение организаций и назначение глобального organization_id**

1. **Соберите очередной JSON-ответ LLM** (organizations[] и contacts[]) из письма/вложений.
2. **Для каждой организации из ответа LLM (organization_id: 1, 2, ...):**
    - Найдите в своей общей базе организаций совпадение:
        - **Ключевые признаки:** название (strict/fuzzy сравнение), ИНН, сайт.
    - Если похожая организация найдена:
        - используйте существующий глобальный organization_id из базы;
        - объедините/обогатите данные (emails, phones, address и т.д.) — новые сведения дописывайте к существующей записи.
    - Если такой организации нет:
        - создайте новую запись в общей базе и присвойте ей новый **глобальный** organization_id (например, автоинкремент).
3. **Сделайте временный маппинг локальных organization_id LLM (например, {1: 101, 2: 107}), чтобы затем обновить ссылки для контактов внутри этого письма.**

***

### **b) Обновление organization_id в персональных контактах**

- Для каждого контакта в массиве contacts[]:
    - Возьмите локальный organization_id (например, 1, 2)
    - Замените на соответствующий **глобальный** organization_id согласно построенному выше маппингу.

***

### **c) Фильтрация и оценка ценности персональных контактов**

- Для каждого контакта выполните функцию оценки (см. ниже).
- В контакты включайте только те, что соответствуют минимальному порогу ценности.
- Контакты без имени/роли и без способов связи (email/phone) не добавляйте — либо сразу на этапе LLM, либо здесь.

```python
def evaluate_contact_value(contact):
    score = 0
    if contact.get('name'): score += 3
    if contact.get('organization'): score += 2
    if contact.get('position'): score += 2
    if contact.get('email'): score += 2
    if contact.get('phone'): score += 2
    if contact.get('city'): score += 1
    if contact.get('inn'): score += 1
    return score >= 4  # Минимальный порог для включения в contacts
```


***

### **d) Контакты e-mail/phone без ФИО и должности:**

- Если контакт не проходит вышеописанную логику (например, только email/phone/website/organization):
    - Такие email/phone добавляйте к organizations (обогащайте массивы emails/phones по найденному глобальному id).
    - Исключайте их из итогового массива contacts.

***

### **e) Обогащение полей**

- Для каждой организации и контакта, если отдельный адрес или город для контакта явно указан — сохраняйте его.
- Если для контакта city/address не указан, копируйте из связанной организации.
- Для организации — накапливайте все новые способы связи, адреса, поступающие из новых данных/писем.

***

### **f) Нормализация и категоризация**

- Нормализуйте формат телефонов и email (чистка пробелов, форматирование, приведение к единому формату).
- Можете дополнительно категоризировать контакты по важности (например, по сумме баллов в evaluate_contact_value).

***

### **Примечание**

- Всегда проверяйте, чтобы в итоговой базе организации были уникальны только по **глобальному** organization_id, независимо от того, сколько раз они встречались в отдельных письмах/парсах.
- Внутри одного письма можно использовать organization_id 1,2… но для общей базы используйте только глобальный id!

***

**В этой схеме, сколько бы парсеров/LLM-вызовов ни было, итоговая БД всегда будет аккуратной, без дублей, и с корректной ссылочной структурой.**

### **4. Изменение промпта в разделе "commercial_offers" (Коммерческие предложения) для LLM**

**Задача:**
Обеспечить, чтобы в массиве "commercial_offers" LLM возвращал только те КП, которые действительно выставлены компанией ООО "ДНК-Технология" конечному клиенту или через посредника. Исключать из массива все случаи, когда КП не было выставлено (запросы, письма по акциям, закрывающие документы без актуального коммерческого, акты выполненных работ и т.д.).

***

#### 📌 **Вставить следующий блок в промпт для LLM (раздел КП):**

> ⚠️ Возвращай коммерческое предложение в массив "commercial_offers" ТОЛЬКО если:
>
> - В письме/вложении (текст) явно присутствует оригинал или копия коммерческого предложения, выставленного от имени компании ООО "ДНК-Технология" (например: заголовок "Коммерческое предложение", "КП"),
> - и имеются четко заполненные: итоговая стоимость (total_cost), дата/номер КП, условия оплаты/поставки, перечень оборудования,
> - и сам документ содержит явные поля предложения: кому выставлено (клиент/партнер), что, когда и на каких условиях.
>
> Не добавляй в commercial_offers:
> - анкеты, заявки на участие в акции, документы "на ознакомление", внутренние запросы, обсуждения, переписку по поводу КП без приложенного оригинала коммерческого,
> - закрывающие документы (счета-фактуры, акты и пр.), если само коммерческое предложение в данном письме/вложении отсутствует,
> - архивные факты старых КП, когда в письме содержится только ссылка/фраза "раньше выставляли КП", но самого нового документа нет.
>
> 💡 Если единственным индикатором КП является только обсуждение (“просим выставить”, “мы выслали”, “приложение к письму” и т.п.), но само предложение (или документ с КП) не приложено — не включай такую запись в массив commercial_offers (верни commercial_offers: []).

### **6. Изменить схему контактов в промпте следующим образом:**

1. Замени поле `"phone": ...` на массив с несколькими номерами.
2. Заведи отдельные поля для разных типов номеров:

```json
"phones": [
  { "type": "office", "number": "+7-960-048-63-74" },
  { "type": "fax", "number": "(843) 258-63-74" }
]
```
3. В инструкции в PROMPT добавь правило:
    - "Если у контакта указано несколько телефонов (телефон, мобильный, факс и др.) — сохраняй все номера в массив."
    - "Если указан тип (например, 'факс', 'рабочий', 'мобильный'), сохраняй тип как поле."
4. В JSON-структуре контакта укажи это поле обязательно как массив (даже если один номер).
