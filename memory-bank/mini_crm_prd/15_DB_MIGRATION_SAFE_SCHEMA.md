# 15_DB_MIGRATION_SAFE_SCHEMA.md

## Назначение
В этом документе описаны правила проектирования схемы базы данных на **MySQL** так, чтобы в дальнейшем можно было **безболезненно мигрировать на PostgreSQL**.  
Задача: максимально быстро реализовать MVP на MySQL, но сохранить совместимость и не «зашить» в схему то, что потом помешает миграции.

---

## Цели
- Исключить использование MySQL-специфичных решений, которые плохо переносятся в PostgreSQL.  
- Сохранить простоту и скорость разработки MVP.  
- Подготовить почву для будущего использования расширенных возможностей PostgreSQL (JSONB, полнотекстовый поиск, pg_trgm и т.д.).

---

## 1. Типы данных

### Универсальные типы
- **Идентификаторы**  
  - Использовать `BIGINT AUTO_INCREMENT` в MySQL.  
  - При миграции → `BIGSERIAL` в PostgreSQL.  

- **Строки**  
  - `VARCHAR(255)` для ограниченных строк, `TEXT` для длинных.  
  - Избегать `ENUM` и `SET` (в PostgreSQL эти типы неудобно расширяются).  
  - Для статусов/ролей использовать справочные таблицы.

- **Булевы значения**  
  - В MySQL хранить как `TINYINT(1)` (`0 = false`, `1 = true`).  
  - При миграции преобразуется в `BOOLEAN`.

- **Дата и время**  
  - Всегда использовать `DATETIME(6)` или `TIMESTAMP(6)`.  
  - Все даты хранить в UTC.  
  - В PostgreSQL будет `TIMESTAMP WITH TIME ZONE`.

- **JSON**  
  - В MySQL использовать тип `JSON`.  
  - При миграции будет преобразован в `JSONB`.  
  - Применять только для обогащённых/второстепенных данных (результаты LLM, метки, полу-структурные поля).

---

## 2. Ключи и ограничения

- У каждой таблицы обязательно **PRIMARY KEY** (`id BIGINT AUTO_INCREMENT`).  
- Для бизнес-идентификаторов (`email`, `ИНН`, `domain`) ставить **UNIQUE**.  
- Избегать MySQL-специфичных `ON UPDATE CASCADE` и `ON DELETE SET NULL`, использовать только если действительно необходимо.  

---

## 3. Индексы

- Делать простые B-Tree индексы для всех полей, используемых в поиске:  
  - `email`, `phone`, `inn`, `city`, `org_name`.  
- Не использовать `FULLTEXT` в MySQL (сложно мигрировать).  
- Для поиска без учёта регистра хранить отдельные «нормализованные» (lowercase) поля + индекс.  

---

## 4. Базовые таблицы (пример)

- **contacts**  
  - `id`, `full_name`, `email`, `phone`, `org_id`, `created_at`, `updated_at`  
  - `UNIQUE(email)` (если не null)  

- **organizations**  
  - `id`, `name`, `inn`, `domain`, `created_at`  
  - Индексы: `inn`, `domain`  

- **interactions**  
  - `id`, `contact_id`, `org_id`, `type`, `content`, `interaction_at`  
  - `TEXT` для `content`  
  - Доп. поле `meta JSON` для LLM-меток, вложенной информации  

---

## 5. Рекомендации по миграции

- Для миграции использовать **pgloader** (поддерживает перенос из MySQL в PostgreSQL с автоматическим преобразованием типов).  
- Проверять схему миграцией на тестовых данных в каждом спринте.  
- Избегать MySQL-специфичных типов: `YEAR`, `ZEROFILL`, `ENUM`, `SET`.  
- Всегда указывать `NOT NULL` там, где поле обязательное.  

---

## 6. Возможности PostgreSQL в будущем

- **GIN/GiST** индексы для `JSONB`.  
- **pg_trgm** для поиска по ФИО, доменам и названиям с опечатками.  
- **Полнотекстовый поиск (FTS)** для заметок, писем, КП (с поддержкой русского языка и ранжированием).  
- **Материализованные представления** для дедупликации и построения скорингов.  

---

## Итог
- Для MVP: простая схема MySQL с переносимыми типами и индексами.  
- Для будущего роста: PostgreSQL даст расширенный поиск, аналитику и работу с JSONB без перестройки модели.  
- Соблюдение этих правил = лёгкая миграция с минимальными изменениями кода и структуры.
