## 🚨 Обнаруженные проблемы

### 1. Использование устаревшего модуля provider_manager.py

**Проблема:**
- В отчете `20250114_1435_api_pipeline_validation.md` указано отключение Groq через `provider_manager.py`
- Согласно коду, `provider_manager.py` помечен как **УСТАРЕВШИЙ** (строка 4-8)
- Новая архитектура использует `UnifiedConfigManager` из `config_manager.py`

**Фактическое состояние:**
- Провайдеры настраиваются через `.env` переменные в `config_manager.py`
- Groq загружается автоматически если есть `GROQ_API_KEY` в `.env`
- Приоритет Groq = 3 (резервный провайдер)

### 2. Некорректные данные в отчете валидации

**Проблема:**
- В отчете указаны данные об "Аппарате УЗИ" и "Эндоскопической стойке"
- Эти данные взяты из **тестового текста** в `main_new.py` (строки 135-155)
- НЕ из реального тестового датасета `test_dataset_10_emails.md`

**Фактические тестовые данные:**
```python
# Из main_new.py, строки 135-155

- Аппарат УЗИ экспертного класса - 2 500 000 руб.

```

### 3. Неправильная интеграция processing_config.json

**Проблема:**
- `processing_config.json` используется только в старом `llm_extractor.py`
- Новый пайплайн `main_new.py` → `ExtractorFactory` → `config_manager.py`
- `config_manager.py` загружает chunking настройки из `processing_config.json` (строки 152-162)

**Фактическая интеграция:**
1. `main_new.py` → `ExtractorFactory.create_test_extractor()`
2. `ExtractorFactory` → `UnifiedConfigManager()`
3. `UnifiedConfigManager.get_processing_config()` → загружает `processing_config.json`
4. Chunking настройки передаются в `ChunkingConfig`

### 4. Отсутствие реального тестирования на датасете

**Проблема:**
- Запрошено тестирование на `test_dataset_10_emails.md`
- Фактически протестирован только встроенный тестовый текст
- Реальные письма из датасета не обрабатывались

**Состав датасета:**
- 10 писем с различными типами вложений (0, 1, 2, 4)
- Реальные коммерческие предложения в PDF
- Письма от dna-technology.ru, centerld.ru
- Содержат ИНН, контактные данные, сайты
