# Отчёт по анализу архитектуры системы обработки контактов

## Цель анализа
Проведён комплексный анализ архитектуры системы для понимания механизмов работы с провайдерами LLM, повторными запросами и обработкой ошибок.

## Проанализированные компоненты

### 1. Основной пайплайн (main_new.py)
- **Функция run_full_pipeline**: Последовательная обработка через Email Service → OCR Service → LLM Extractor → Export Service
- **Функция run_test_mode**: Тестирование извлечения контактов из текста
- **Валидация зависимостей**: Проверка конфигурации перед запуском
- **Режимы работы**: Интерактивный, тестовый, валидационный, полный пайплайн

### 2. OCR процессор (ocr_processor.py)
- **Метод _get_existing_result**: Загрузка уже обработанных результатов OCR
- **Кэширование**: Проверка существующих результатов по имени файла
- **Обработка форматов**: Поддержка различных типов вложений
- **Разделение результатов**: Успешные и ошибочные файлы

### 3. API валидатор пайплайна (api_pipeline_validator.py)
- **Метод process_single_email**: Обработка одного письма с вложениями
- **Метод _extract_text_content_via_main_pipeline**: Извлечение текста через OCR Service
- **Интеграция с IntegratedLLMProcessor**: Обработка через LLM с fallback механизмами
- **Проверка успешности**: Валидация результатов обработки

### 4. Фабрика экстракторов (extractor_factory.py)
- **Метод create_extractor**: Создание ContactExtractor с полной конфигурацией
- **Метод validate_dependencies**: Проверка API ключей, промптов и конфигураций
- **Инициализация компонентов**: UnifiedConfigManager, ProviderManager, PhoneNormalizer, LLMResponseValidator
- **Настройка конфигураций**: ChunkingConfig и RetryConfig

### 5. Менеджер провайдеров (provider_manager_old.py) - удалён, как устарешний!
- **Метод make_request_with_fallback**: Система fallback между провайдерами
- **Приоритизация провайдеров**: OpenRouter (приоритет 2), Groq (приоритет 3)
- **Ограничение попыток**: max_fallback_attempts = 2
- **Обработка ошибок**: Сбор ошибок от всех провайдеров
- **Статистика**: Отслеживание использования провайдеров

### 6. Унифицированный менеджер конфигурации (config_manager.py)
- **Приоритеты провайдеров**: Replicate (1), OpenRouter (2), Groq (3)
- **Конфигурация повторных попыток**: max_retries, retry_delay, rate_delay, retry_base, retry_jitter
- **Валидация конфигурации**: Проверка провайдеров, IMAP, экспорта
- **Загрузка из .env**: Автоматическая загрузка переменных окружения

## Ключевые архитектурные особенности

### Система провайдеров
1. **Приоритизация**: Replicate → OpenRouter → Groq
2. **Fallback механизм**: Автоматическое переключение при ошибках
3. **Ограничение попыток**: Максимум 2-3 попытки на провайдера
4. **Конфигурация из .env**: Централизованное управление API ключами

### Обработка повторных запросов
1. **Экспоненциальная задержка**: retry_base = 1.6, retry_jitter = 0.4
2. **Максимальные попытки**: retry_max = 6
3. **Rate limiting**: rate_delay = 1.2 секунды
4. **Fallback к Replicate**: Автоматическое переключение при исчерпании попыток

### Кэширование и оптимизация
1. **OCR кэширование**: Проверка существующих результатов
2. **Chunking**: Токен-базированное разделение текста (4000 токенов с перекрытием 400)
3. **Параллельная обработка**: max_parallel = 3
4. **Пропуск обработанных**: skip_processed = true

### Валидация и контроль качества
1. **Валидация зависимостей**: Проверка API ключей, промптов, конфигураций
2. **LLM Response Validator**: Валидация ответов от LLM
3. **Confidence threshold**: 0.6 для экспорта результатов
4. **Phone Normalizer**: Нормализация телефонных номеров

## Выявленные проблемы и рекомендации

### Проблемы
1. **Отсутствие JSON валидации**: Нет проверки структуры ответов LLM
2. **Неинтегрированный постпроцессинг**: src/postprocessing не используется в основном пайплайне

### Рекомендации
1. **Добавление JSON валидации**: Проверка структуры ответов после LLM обработки
2. **Интеграция постпроцессинга**: Включение нормализации телефонов в основной пайплайн
3. **Улучшение мониторинга**: Расширенная статистика использования провайдеров

## Заключение
Архитектура системы хорошо структурирована с четким разделением ответственности. Реализованы надёжные механизмы fallback и retry логики. Основные области для улучшения: унификация конфигурации, добавление JSON валидации и интеграция постпроцессинга.
