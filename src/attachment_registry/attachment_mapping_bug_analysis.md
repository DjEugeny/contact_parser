# Анализ бага маппинга вложений в Advanced Email Fetcher

## Описание проблемы

В модуле `src/advanced_email_fetcher.py` обнаружена критическая проблема с некорректным маппингом вложений между письмами в одном треде (thread). Проблема заключается в том, что вложения от одного письма в треде ошибочно приписываются другим письмам этого же треда.

### Симптомы

1. **Неправильный список вложений**: В JSON файлах писем указаны вложения, которых в этих письмах нет
2. **Дублирование вложений**: Одно и то же вложение появляется в нескольких письмах треда
3. **Нарушение бизнес-логики**: При анализе summary письма и interaction для участников треда используется неверная информация о вложениях

### Конкретные примеры

**Пример 1 - thread_id: `20250723_dna-technology_ru_be4fb59a`**
- Письмо `email_003.json` (без вложений) показывает 2 вложения:
  - `АНКЕТА Участника.docx`
  - `Письмо для пользователей 1.1.doc`
- Письмо `email_006.json` (с вложениями) корректно показывает те же 2 вложения

**Пример 2 - thread_id: `20250723_dna-technology_ru_1c456124`**
- Письмо `email_004.json` (1 вложение) показывает 3 вложения: `КП 8386 от 23.07.2025.pdf`
- Письмо `email_009.json` (0 вложений) показывает те же 3 вложения
- Письмо `email_012.json` (0 вложений) показывает те же 3 вложения
- Письмо `email_014.json` (1 вложение) показывает те же 3 вложения

## Корневая причина

### Проблемный код

В методе `check_email_processing_status()` (строки 2600-2615) используется `thread_id` для поиска вложений:

```python
# Ищем файлы вложений по thread_id из JSON
thread_id = email_data.get("thread_id", "")
if thread_id:
    # Ищем файлы с префиксом thread_id
    attachment_files = list(
        attachments_path.glob(f"*{thread_id}*")
    )
    if attachment_files:
        status["attachments_exist"] = True
        status["attachment_files"] = [
            str(f) for f in attachment_files
        ]
```

### Почему это неправильно

1. **Thread ID не уникален для вложений**: Все письма в одном треде имеют одинаковый `thread_id`, но вложения прикреплены к конкретным сообщениям
2. **Message ID уникален**: Каждое письмо имеет уникальный `message_id`, который должен использоваться для идентификации вложений
3. **Файловая структура не разделяет вложения**: Файлы вложений命名 с использованием `thread_id`, что приводит к путанице

### Текущая логика именования файлов

В методе `save_attachment_or_inline()` (строки 1620-1623):
```python
prefix = "inline" if is_inline else "attach"
unique_filename = f"{thread_id}_{timestamp}_{prefix}_{safe_filename}"
```

Это означает, что файлы вложений именуются с `thread_id`, а не с `message_id`.

## Последствия

1. **Неверная бизнес-аналитика**: Система анализа коммерческих предложений работает с некорректными данными
2. **Неправильное взаимодействие**: При анализе interaction для каждого участника треда используется неверная информация о вложениях
3. **Дублирование данных**: Одно и то же вложение учитывается несколько раз в различных письмах
4. **Нарушение целостности данных**: База данных содержит некорректные связи между письмами и вложениями

## Решение

### Фаза 1: Быстрое исправление (1-2 дня)

1. **Изменить именование файлов**: Использовать `message_id` вместо `thread_id` для новых вложений
2. **Исправить логику поиска**: Искать вложения по `message_id` в `check_email_processing_status()`
3. **Обновить обработку сценария download_json**: Правильно обрабатывать случай, когда вложения есть, а JSON нет

### Фаза 2: Реестр вложений (2-3 дня)

1. **Создать централизованный реестр**: Класс `AttachmentRegistry` для точного отслеживания связей
2. **Интегрировать в AdvancedEmailFetcherV2**: Заменить прямую работу с файлами на реестр
3. **Обеспечить обратную совместимость**: Адаптеры для существующих модулей

### Фаза 3: Миграция данных (1-2 дня)

1. **Разработать скрипт миграции**: Перенести существующие данные в новую систему
2. **Обработать осиротевшие вложения**: Найти и зарегистрировать вложения без записей
3. **Валидация результатов**: Проверить корректность миграции

## Технические детали

### Структура реестра вложений

```json
{
  "attachments": {
    "attachment_id": {
      "message_id": "уникальный ID сообщения",
      "attachment_filename": "оригинальное имя файла",
      "attachment_path": "путь к файлу",
      "thread_id": "ID треда",
      "file_size": 12345,
      "content_type": "application/pdf",
      "is_inline": false,
      "registered_at": "2025-01-01T00:00:00Z"
    }
  },
  "messages": {
    "message_id": {
      "thread_id": "ID треда",
      "attachment_ids": ["attachment_id1", "attachment_id2"],
      "total_attachments": 2
    }
  }
}
```

### Изменения в AdvancedEmailFetcherV2

1. **Метод save_attachment_or_inline()**:
   - Генерация attachment_id на основе message_id и имени файла
   - Регистрация вложения в реестре
   - Сохранение файла с message_id в имени

2. **Метод check_email_processing_status()**:
   - Поиск вложений по message_id через реестр
   - Проверка существования файлов

3. **Метод process_single_email()**:
   - Использование реестра для получения информации о вложениях
   - Корректная обработка всех сценариев

### Адаптеры для обратной совместимости

1. **OCR Processor Adapter**: Обеспечивает доступ к вложениям через message_id
2. **File Tokens Adapter**: Адаптирует логику токенов к новой системе
3. **Contact Phone Adapter**: Обеспечивает корректную работу с вложениями контактов
